# 阶段六：网络条件与性能验证

> 上游蓝本：[mirror-physics-interaction-plan.md](../mirror-physics-interaction-plan.md) 第 10 节阶段六、第 11、12 节
> 前置依赖：阶段五全部完成标准达成
> 编写日期：2026-09-15

## 1. 阶段目标

在不改玩法逻辑的前提下，用 Latency Simulation Transport 复现非理想网络条件，验证交互稳定性、对象生命周期正确性与服务器性能上限，产出数据表与最终验收结论，作为蓝本第 12 节验收的执行依据。

## 2. 前置条件

- [ ] 三类道具在理想网络下 4 人冒烟通过。
- [ ] 阶段三记录的起始同步参数（频率/缓冲/字节数）可用作对比基线。

## 3. 任务清单

### 3.1 延迟模拟环境

- 在客户端与服务器连接间启用 Latency Simulation Transport（或等价配置），参数化：延迟、丢包率、乱序。
- 定义标准场景脚本：4 人进入 → 推箱 → 抓取投掷 → 拉杆 → 部分玩家退出/重进 → 循环。

### 3.2 网络条件矩阵

| 用例 | 延迟 | 丢包 | 通过口径 |
|---|---|---|---|
| 理想 | 0ms | 0% | 全流程无异常 |
| 局域网上限 | 80ms | 0-1% | 交互可用，插值无跳变 |
| 劣质网络 | 150ms | 5%（含乱序） | 交互可用，无对象生命周期错误 |

- 每档条件记录：交互可感知延迟、远端道具观感、断线重连是否正确。

### 3.3 生命周期与失败场景

- 非 0ms 条件下重复蓝本第 11 节关键项：Late Join、主动离开、非正常断开、道具运动中玩家离开、连续回收重用、池容量不足、重复 Spawn 防护。
- 场景重新加载：确认池与网络对象正确清理重建。
- 所有失败路径必须有明确日志（找不到对象、校验失败、池耗尽等），不允许静默失败。

### 3.4 性能采集

- 采集并记录（表格落盘到本阶段执行记录）：
  - 服务器 Tick/帧率（4 人 + 约 12 个动态物理对象，含持续运动与睡眠混合态）。
  - 带宽：单客户端上下行 KB/s（理想条件与 150ms 条件）。
  - 池使用峰值：各道具同时活跃数、是否触及容量警告。
  - 客户端帧率与插值缓冲表现。

## 4. 完成标准

- [ ] 0ms / 80ms / 150ms 延迟档全部通过交互口径。
- [ ] 低比例丢包（≤5%，含乱序）下网络对象生命周期零错误。
- [ ] 4 人 + 12 动态物理对象时服务器稳定运行（≥15 分钟压力循环，无内存持续增长、无帧率崩塌）。
- [ ] 所有失败场景有明确日志。
- [ ] 性能数据表与本阶段结论已写入执行记录。

## 5. 最终验收对照（对应蓝本第 12 节）

本阶段结束时逐条核对蓝本第 12 节「技术框架验收」12 项与「文档验收」5 项，逐项打勾；任何一项不满足，回退到对应阶段文档处理，不在此阶段打补丁绕过。

特别确认：旧 `LocalServer` 全程未参与新玩法。

## 6. 风险与回退

| 风险 | 处理 |
|---|---|
| 150ms + 丢包下插值崩坏 | 优先调插值缓冲与同步频率（用阶段三基线对比）；仍不达标则记录为首版已知限制，列入未来升级路线 |
| 性能不达标 | 先定位瓶颈（物理 Tick / 同步频率 / 池行为），按定位结果回对应阶段调参；不引入第三方插件 |
| Latency Simulation 无法模拟乱序 | 记录为测试环境限制，用丢包+延迟组合近似覆盖，并在执行记录注明 |
