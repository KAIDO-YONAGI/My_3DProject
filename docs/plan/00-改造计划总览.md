> 上游蓝本：[物理派对游戏技术选型与实施计划](../Mirror框架物理交互游戏开发计划.md)
>
> 文档性质：阶段索引、执行顺序和全局约束

## 1. 执行目标

计划围绕 2～5 人物理乱斗垂直切片展开，按以下顺序形成可运行结果：

```text
玩法规格
  → 单机回合闭环
  → 核心对抗手感
  → 道具、事件与机器人
  → 展示质量
  → 固定 Tick 状态模型
  → 服务器权威同步
  → 预测、校正与弱网验证
```

每个阶段完成一项独立可验收的交付。阶段验收通过后进入下一阶段。

## 3. 全局架构约束

1. 单机玩法能够独立完成整局。
2. 真人、机器人、回放和网络输入使用同一种输入帧。
3. 玩法状态由固定 Tick 模拟推进。
4. Unity 表现层读取状态并播放动画、音效、粒子和 UI。
5. 联机客户端提交输入帧，服务器生成最终状态。
6. 伤害、淘汰、得分、爆炸和胜负由服务器结算。
7. 远端对象使用状态快照和插值。
8. 本地预测聚焦角色移动、跳跃和冲刺。
9. 道具与事件具有统一生命周期和重置清单。
10. 每项展示材料与可运行结果保持一致。

## 4. 首版玩法范围

### 4.1 竞技场

- 一张圆形或近圆形竞技场。
- 出生点、复活点和 KillZone。
- 道具刷新点。
- 酸雨安全区。
- 可配置障碍物。

### 4.2 玩家能力

- 移动。
- 跳跃。
- 冲刺。
- 推挤。
- 拾取。
- 投掷。
- 受击。
- 死亡和复活。

### 4.3 动态内容

- 2～3 种颜色药水。
- 一种爆炸投掷物。
- 一种酸雨事件。
- 一个基础机器人。

### 4.4 后续内容

- 怪物事件。
- 多张正式地图。
- 精彩片段回放。
- 任意网格破坏。
- 局部道具预测。
- 匹配、大厅和正式部署。

## 5. 阶段闸门

| 进入阶段 | 必须满足 |
|---|---|
| 阶段二 | 玩法规则完整，原型场景可运行 |
| 阶段三 | 单机回合可连续运行 10 局 |
| 阶段四 | 核心动作和淘汰归属稳定 |
| 阶段五 | 机器人、药水、爆炸物和酸雨可完成整局 |
| 阶段六 | 单机垂直切片具备展示质量 |
| 阶段七 | 固定 Tick 和三局输入回放通过 |
| 阶段八 | 双客户端服务器权威整局稳定 |

## 6. 每阶段交付格式

每个阶段交付包含：

- 可运行场景或构建。
- 通过标准对应的验证结果。
- 当前参数基线。
- 已知风险和下一阶段输入。

## 7. 投入约束

求职阶段每周投入控制在个人有效学习时间的 20%～25%。每周只安排一个主要交付，优先完成可运行和可展示结果。
