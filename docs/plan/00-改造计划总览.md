# 物理派对游戏执行计划总览
## 1. 执行目标
完成 2～5 人物理乱斗垂直切片：一张竞技场、完整比赛循环、核心角色动作、颜色药水、爆炸物、酸雨、基础机器人、展示材料和 Mirror 服务器权威联机样片。
首版采用受约束角色运动、服务器权威玩法模拟和可恢复平台状态。客户端提交输入意图，不提交权威位置；服务器固定 Tick 推进 `GameState` 并决定最终状态。Mirror 负责连接、网络对象、权限和消息分发。客户端对本地角色做输入预测与服务器校正，对远端对象做快照插值。Unity Transport、自研 UDP 新链路、NetworkRigidbody 核心同步、任意网格破坏和完整物理回滚不进入首版。
### 当前基线与目标
截至 2026-10-08，工程的玩家位置同步仍是客户端权威：本地客户端运行角色运动，`NetworkTransformReliable` 以 `ClientToServer` 同步，服务器接收并转发位置。本文描述迁移目标，不表示服务器权威或预测校正已经实现；当前配置事实以 [Mirror_KCP_Config.md](../../Y_MultipleAgentWorkflow/UnityRuntime/Mirror_KCP_Config.md) 和实际代码、Prefab 为准。
迁移分三步：阶段六拆分输入、运动状态与表现；阶段七让服务器真正运行运动和碰撞，并改为输入上行、快照下行；阶段八加入本地预测、状态恢复和输入重放。仅将 `NetworkTransform` 改为 `ServerToClient` 无法完成迁移。

## 3. 全局技术约束
1. 单机完整可运行后进入联机；
2. 真人、机器人、回放和网络输入统一为 `InputFrame`；网络客户端只能提交经过服务器校验的输入意图；
3. 玩法由固定 Tick 推进，表现层只读状态与事件；
4. 服务器是移动、碰撞、伤害、击退、淘汰、计分、道具、事件和胜负的唯一权威；
5. Mirror 负责网络层能力，不替代玩法模拟；
6. 本地角色移动、跳跃和冲刺使用预测、确认与输入重放；远端对象使用快照插值；共享刚体和玩法结果不做客户端权威预测；
7. 道具、事件和平台状态统一生命周期和重置入口。
## 4. 阶段闸门
阶段二要求规则和原型场景可运行，并由单一模拟入口推进角色状态；阶段三要求单机连续 10 局且动作、击退和归属由模拟状态结算；阶段四要求玩家与机器人共享输入帧并完成完整比赛；阶段五要求单机展示材料完成且表现层不成为玩法状态来源；阶段六要求固定 Tick 输入回放关键结果一致；阶段七要求服务器独占权威模拟、双客户端通过服务器状态完成整局；阶段八要求本地预测可校正、弱网整局稳定。
## 5. 交付原则
每阶段交付可运行场景或构建、配置基线、验证结果、风险和下一阶段输入。每周安排一个主要交付，求职阶段投入控制在个人有效学习时间的 20%～25%。
