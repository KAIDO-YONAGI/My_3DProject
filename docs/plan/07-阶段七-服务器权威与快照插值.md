# 阶段七：Mirror 服务器权威与快照插值
> 前置：阶段六完成；交付：双客户端可连续完成整局的 Mirror 联机样片
## 1. Mirror 工程接入
使用 Mirror NetworkManager 管理服务器、客户端、场景和连接生命周期，使用 KCP Transport 建立首版实时连接。玩家对象使用 NetworkIdentity 和客户端拥有权限提交输入，服务器对象和共享道具保持服务器权限。
服务器使用 Unity Server Build，不创建客户端表现，不读取本地输入。客户端与服务器共享协议数据结构和序列化规则，玩法模拟程序集不依赖 Unity 表现层。
## 2. 输入与服务器 Tick
客户端通过 Command 或自定义 NetworkMessage 上传带协议版本、输入序号、目标 Tick 和输入帧的消息。服务器验证连接与玩家映射、序号、Tick 范围、移动向量、动作位、输入频率和包体长度。
服务器每 Tick 为每名玩家选择输入，缺失输入使用明确策略，推进权威 `GameState`，处理角色、道具、酸雨、伤害、淘汰、计分和胜负，再更新已处理输入序号并生成快照。
## 3. 快照与 Mirror 组件
快照包含服务器 Tick、快照序号、已处理输入序号、玩家状态、道具状态、回合状态和事件状态。低频回合、分数、存活和持有关系可使用 SyncVar；高频连续状态使用自定义快照，不把大量物理字段拆成可靠 RPC。
远端玩家、爆炸物和移动障碍物按服务器 Tick 排序并写入快照缓冲，在目标显示 Tick 上插值。死亡、复活、拾取、爆炸、药水和回合转换使用可靠事件或可恢复状态。
NetworkTransform 仅用于经过验证的简单展示对象。NetworkRigidbody 不作为首版核心同步方案，复杂物理由服务器计算，客户端显示服务器快照。
## 4. 加入、Late Join 与断线
```text
连接 → 协议和容量验证 → 创建玩家标识 → 发送当前 GameState
→ 进入快照流 → 参与后续回合
```
Late Join 必须获得当前 Tick、回合、玩家、活跃道具、药水、酸雨和平台状态。主动离开和超时断线统一清理玩家、持有道具、药水来源、归属记录、观察者关系和临时对象。
## 5. 完成标准与测试
□ KCP Server Build 可独立启动；
□ 两个客户端可加入同一比赛；
□ 输入经过服务器校验；
□ 两客户端连续多局结果一致；
□ 远端角色和道具插值稳定；
□ Late Join 状态完整；
□ 主动离开与异常断线清理完整；
□ 随后扩展到五客户端；
□ Tick、快照、输入和带宽可观测。
测试同时加入、逐个加入、回合中 Late Join、结算时 Late Join、主动离开、进程关闭、持有爆炸物离开、药水期间离开、快照重复、乱序和间隔波动。Mirror 权限、可靠事件幂等和对象生命周期作为独立验收项。
