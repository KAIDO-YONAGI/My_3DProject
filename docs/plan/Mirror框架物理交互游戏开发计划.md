# Mirror 框架物理交互游戏开发计划
## 1. 项目目标
项目面向 2～5 人短回合物理乱斗。玩家通过移动、跳跃、冲刺、推挤、拾取和投掷争夺胜利，随机道具、障碍物和全局事件改变场地节奏。
首版交付一张竞技场、完整回合与比赛流程、核心角色动作、2～3 种颜色药水、一种可踢动和投掷的爆炸物、一种酸雨事件、一个基础机器人，以及可运行构建、演示视频、README 和架构图。联机交付 Mirror 服务器权威样片、远端插值、本地角色预测、弱网验证和指标面板。
怪物事件、完整精彩回放、任意网格实时破坏、多张正式地图、匹配大厅、账号系统、正式服务器编排和完整物理回滚进入后续范围。爆炸对平台的影响采用可恢复预制状态、临时缺口或危险区域。
### 当前实现与计划目标
截至 2026-10-08，工程玩家运动仍由本地客户端计算，通过 `NetworkTransformReliable` 的 `ClientToServer` 上行并由服务器转发；现有角色使用 `CharacterController`，不是完整刚体角色。服务器权威、输入上传和预测校正是本计划的迁移目标，不是当前已完成能力。
当前配置以 [Mirror_KCP_Config.md](../../Y_MultipleAgentWorkflow/UnityRuntime/Mirror_KCP_Config.md) 和实际代码、Prefab 为准。迁移不是只改同步方向：先拆出输入和可恢复运动状态，再使专用服务器运行运动/碰撞，改为输入上行与快照下行，最后增加本地预测与校正。具体改造职责见阶段六至八。
## 2. 玩法规则
比赛由多个短回合组成。每次淘汰为对应对手增加一分，目标分数、最大回合数、单回合时长、复活次数、复活延迟和复活保护进入配置。阶段一选择并冻结一套首版参数。
生命值耗尽和进入 KillZone 共用淘汰流程，每次死亡只创建一条淘汰记录。直接伤害使用最近有效攻击者，推挤后掉落使用归属时间窗内最近有效作用者，酸雨和纯环境伤害进入环境统计。同 Tick 多人淘汰按照固定顺序结算。
药水通过颜色区分，饮用前只知道颜色，饮用后揭示效果。首版从加速、中毒、致盲中选择 2～3 种，每种效果定义持续时间、叠加规则、状态提示和结束清理。
爆炸物支持推动、踢动、拾取和投掷，倒计时持续推进，爆炸产生范围伤害和击退。最近有效持有者、投掷者或作用者参与归属。酸雨包含预警、生效和结束阶段，怪物事件在基础事件稳定后实施。
## 3. 技术选型
| 领域 | 首版选型 |
|---|---|
| Unity | `2022.3.62f3c1` |
| 网络框架 | Mirror |
| 默认传输 | Mirror KCP Transport |
| 服务器 | Unity Dedicated Server / Server Build |
| 玩法模型 | 普通 C# 状态数据和固定 Tick 模拟 |
| 模拟频率 | 30Hz 起步，以实测结果调整 |
| 角色运动 | 受约束胶囊运动、碰撞查询和速度上限 |
| 动态道具 | 服务器 Unity PhysX |
| 远端显示 | 状态快照和插值 |
| 本地响应 | 受约束角色移动、跳跃和冲刺的非权威预测与服务器校正 |
| 回放 | 输入记录、随机状态和关键事件验证 |
### 3.1 Mirror 的职责
Mirror 负责服务器和客户端启动、连接管理、场景切换、玩家生成、`NetworkIdentity` 生命周期、对象权限、`Command`、`ClientRpc`、`TargetRpc`、`SyncVar`、网络消息、观察者和 Transport 接入。
Mirror 不直接承载核心规则。服务器模拟状态是玩家位置、旋转、速度、碰撞、命中、伤害、淘汰、计分、道具、事件和胜负的唯一事实来源。`NetworkBehaviour` 负责验证并把输入送入服务器队列，再把权威快照和事件发送到客户端。客户端对象所有权仅允许提交请求，不授予最终状态写入权。
### 3.2 Transport 选择
首版使用 Mirror KCP Transport。加入、离开、拾取确认、爆炸、复活、回合转换和结算等离散事件使用可靠通道；高频位置和速度快照使用可丢弃通道。Unity Transport 与自研 UDP 新链路不进入首版实现。
### 3.3 权限模型
玩家对象可以由对应客户端拥有，使客户端能够提交输入；玩家位置、旋转、速度、碰撞、生命和动作结果仍由服务器模拟与确定。客户端不得直接上传或覆盖最终 Transform。药水、爆炸物、平台状态、事件对象和机器人保持服务器权限，客户端对拾取、投掷和使用行为只发送请求。
### 3.4 同步组件
`SyncVar` 适合回合阶段、分数、存活状态和持有关系等低频状态。高频角色和道具状态使用自定义快照，包含服务器 Tick、快照序号、玩家最近已处理输入序号和客户端校正所需的运动状态，避免大量连续物理字段走独立可靠同步。
玩家权威位置不使用 `NetworkTransform` 客户端上行同步。`NetworkTransform` 仅用于经过验证的非权威展示对象；不得与快照接收器同时写同一个玩家 Transform。`NetworkRigidbody` 不作为首版核心物理同步方案，复杂物理由服务器模拟，客户端远端插值、本地预测和校正。
## 4. 总体架构
```text
输入设备 / 机器人 / 回放 → InputFrame → 固定 Tick 玩法模拟 → GameState → Unity 表现
客户端采集 InputFrame → Mirror Command / NetworkMessage → 服务器校验与输入队列
→ 服务器固定 Tick 权威模拟 → StateSnapshot + 离散事件
→ 本地玩家：确认 / 校正 / 重放；远端对象：快照缓冲 / 插值
```
Mirror 网络对象承担身份、生命周期和连接关系，普通状态结构承担玩法规则，表现层只读取状态和事件。
## 5. 状态与消息
`InputFrame` 包含玩家标识、输入序号、目标 Tick、移动方向、朝向意图、跳跃、冲刺、拾取、投掷、使用药水和瞄准方向。真人、机器人、回放和网络输入使用同一格式。输入帧不包含用来覆盖权威模拟的玩家位置、速度或命中结果。
`PlayerState` 保存位置、旋转、速度、动作、生命、生存状态、冲刺冷却、药水、持有道具、最近有效作用和分数；`ItemState` 保存类型、实例标识、位置、旋转、速度、生命周期、持有者、倒计时和效果参数；`RoundState` 保存阶段、Tick、计分、胜者、复活队列和事件状态。
运动状态必须覆盖水平/垂直速度、接地、动作计时、冷却、输入缓冲和击退等重演依赖项，并支持保存与恢复。相机相对输入在客户端采集时转换成世界水平面方向，模拟不读取 `Camera.main`；普通状态不持有 Unity 对象引用，碰撞适配器仍可使用 Unity。
输入消息携带协议版本、输入序号、目标 Tick 和若干输入帧。服务器校验连接与玩家映射、序号、Tick 窗口、向量与朝向范围、动作位、输入频率、队列容量和包体长度。快照携带服务器 Tick、快照序号、各玩家最近已处理输入序号、客户端预测校正所需的玩家运动状态、道具状态、回合状态和事件状态；快照以服务器模拟结果为准。
每玩家每服务器 Tick 至多消费一帧有效输入；缺帧可短暂沿用持续输入，但不能重复触发单次动作。输入确认在模拟完成后产生，协议须区分已执行与最终丢弃输入，提供可清理历史的连续确认语义。快照携带比赛/回合代次和重置标识，防止旧状态跨复活或重开覆盖新状态。
## 6. 固定 Tick 与物理
服务器以 30Hz 起步，按固定顺序读取并选择输入、更新回合、更新角色、处理碰撞与推挤、更新道具、更新药水、更新酸雨、处理死亡与计分、生成事件并输出状态。服务器是网络比赛中唯一推进权威 `GameState` 的模拟者。
角色运动使用受约束模型，明确地面、空中、冲刺、击退和垂直速度上限。动态道具使用服务器 PhysX，服务器 Tick 与物理步进保持单一入口。浮点数和 PhysX 不提供跨机器位级确定性，输入回放只验证同一运行环境中的关键结果。客户端预测仅为本地手感运行近似模拟，预测差异必须以服务器状态校正，不构成第二权威来源。
## 7. 快照、预测与校正
远端玩家、爆炸物和移动障碍物进入按服务器时间排序的快照缓冲，在延迟显示时间上插值。死亡、拾取、爆炸、药水、复活和回合转换通过可靠事件或可恢复的权威状态应用。
本地预测只覆盖受约束角色移动、跳跃和冲刺。客户端保存未确认输入，快照携带服务器已处理输入序号和必要的权威运动状态；客户端恢复权威状态、删除已确认输入、按序重放待确认输入。误差修正可以平滑视觉，但玩法状态立即以服务器确认结果为基准。拾取、投掷和饮用可以播放可撤销的即时动画与提示，持有关系、投掷轨迹、药水效果、伤害、淘汰、计分和胜负等待服务器结果。
误差比较必须对齐同一确认 Tick，校正恢复全部运动状态而不只是位置；平滑仅作用于视觉节点，重演不重复触发音效等一次性副作用。输入历史有界，死亡、复活和回合转换重建权威基准；首版不回滚共享 PhysX 世界，动态碰撞偏差接受服务器校正。Host 避免权威模拟和本地预测对同一根节点重复推进。
## 8. 实施阶段
1. 玩法规格与工程基线：冻结比赛、输入、归属、药水、爆炸物和酸雨规则。
2. 单机回合闭环：完成移动、生命、淘汰、复活、计分、结算和重开。
3. 手感、冲刺与推挤：完成输入缓冲、冲刺、击退、命中和归属。
4. 道具、事件与机器人：完成药水、爆炸物、酸雨、机器人和重置。
5. 展示质量：完成镜头、动画、音效、粒子、UI、构建和材料。
6. 固定 Tick 与状态模型：抽取输入、状态、事件和输入回放。
7. Mirror 服务器权威同步：完成 KCP、Server Build、玩家生成、输入上传、快照和远端插值。
8. 预测、校正与弱网：完成角色预测、校正、2～5 人验证和指标。
## 9. 验收与风险
单机连续完成 10 局，玩家与机器人可以完成完整比赛。三局输入回放的胜者、分数和淘汰顺序一致。Server Build 与两个客户端连续完成多局后扩展到五个客户端；验证客户端伪造位置或命中结果不能改变服务器权威状态。
Mirror 验收覆盖 KCP 连接、输入权限与校验、初始状态、远端快照插值、本地输入确认与校正、可靠事件幂等、Late Join、主动离开、异常断线、持有爆炸物离开和回合重开。Host 与 Dedicated Server 均验证相同的权威边界。
规则同时写入 Mirror 组件和玩法状态会形成双重事实来源，所有结算集中到服务器模拟状态。共享物理权限会造成竞争与作弊风险，共享道具保持服务器权限。高频状态全部使用可靠 RPC 会造成阻塞和带宽增长，连续状态使用快照。完整物理预测和任意平台破坏扩大范围，首版限定为本地角色运动预测和预制平台状态；客户端所有权不等于状态权威。
