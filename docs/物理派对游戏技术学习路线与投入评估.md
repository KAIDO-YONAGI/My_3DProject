# 物理派对游戏技术路线与执行计划

## 目标与定位

这个项目是长期兴趣项目，也可以逐步产出适合求职展示的作品。求职阶段不把它作为开始投递的前置条件，先完成能够运行、能够试玩、能够讲清楚的核心结果，再根据时间进入联机技术深度。

近期目标是完成一个可玩的物理派对游戏垂直切片，包含清晰的操作手感、完整回合流程、可录制视频、README 和架构图。联机部分按照单机闭环、展示质量、稳定同步、预测校正的顺序推进。

求职阶段每周用于本项目的时间控制在个人有效学习时间的 20% 至 25%。项目新增内容不能挤占投递、算法训练、八股准备和面试复盘。拿到实习后，再根据工作节奏继续扩展联机和服务器能力。

## 目标技术路线

项目采用单机玩法、固定 Tick 状态模型、服务器权威同步和有限客户端预测的路线。核心玩法使用受约束的角色运动与简化推挤。Unity 负责场景、动画、镜头、音效和视觉表现。传输层使用 Unity Transport 2.x，只承担字节收发与连接管理；输入帧、权威状态、快照插值、预测校正和指标采集全部自研。

```text
输入采集
  → 固定 Tick 玩法模拟
  → 单机与机器人完整回合
  → 可运行构建与展示材料
  → 服务器权威处理输入
  → 客户端接收状态快照
  → 远端角色插值
  → 本地角色预测与校正
  → 延迟和丢包模拟
```

### 目标选型

| 决策项 | 选定结果 |
|---|---|
| 引擎与工程 | Unity 2022.3.62f3c1，现有工程 |
| 传输层 | Unity Transport 2.x，传输调用收口在 ITransport 接口后 |
| 网络游戏层 | 自研输入帧、服务器 Tick、状态快照、插值、预测与校正 |
| 服务器形态 | 无图形专用服务器，以 Server Build 构建；服务器不是玩家，没有本地角色和本地输入 |
| 模拟频率 | 30Hz 固定 Tick，30Hz 快照；输入按渲染帧采样、按 Tick 聚合 |
| 角色运动 | 自定义胶囊状态与 Tick 运动逻辑，Unity 物理只用于碰撞查询 |
| 数值 | 浮点数 |

## 近期展示目标

1. 一张圆形竞技场。
2. 玩家能够移动、跳跃、冲刺和推挤。
3. 玩家掉落后能够复活，回合能够计分、结束和重开。
4. 单机模式能够连续完成完整回合，操作反馈和结果反馈清晰。
5. 一个能够完成基本对抗的机器人使用与玩家相同格式的输入帧。
6. 形成可运行构建、60 至 90 秒视频、README 和一张简洁架构图。

## 联机阶段目标

1. 将玩法状态和表现层分离，固定 Tick 驱动关键状态。
2. 服务端接收输入、推进权威模拟、发送状态快照。
3. 客户端对远端角色进行快照插值。
4. 在双客户端稳定完成整局后，再加入本地预测与服务器校正。
5. 使用延迟、抖动和丢包模拟验证同步质量，并展示 RTT、预测误差、校正次数和收发字节数。

## 开发管线

玩法规格 → 工程基线 → 回合骨架 → 移动与跳跃 → 冲刺与推挤 → 掉落与复活 → 胜负与重开 → 手感与反馈 → 录制与材料 → 固定 Tick → 服务端权威同步 → 远端插值 → 本地预测与校正 → 弱网验证 → 构建与投递材料。

项目始终按照可运行结果推进。单机闭环和展示材料完成后，再决定是否进入联机深度阶段。

## 系统边界

| 模块 | 职责 | 完成标准 |
|---|---|---|
| 玩法模拟 | 处理输入、角色状态、推挤、掉落和回合规则 | 固定 Tick 下可以单独运行并记录状态 |
| Unity 表现 | 显示模拟结果，处理动画、镜头、音效、粒子和 UI | 表现逻辑不修改玩法状态 |
| 机器人 | 根据当前状态生成与玩家相同格式的输入 | 单人模式可以稳定完成整局 |
| 服务器 | 接收输入、推进权威模拟、发送状态快照 | 两个客户端得到一致胜负结果 |
| 客户端 | 采集输入、插值远端状态、预测本地移动、处理校正 | 延迟环境下保持可操作，误差可以测量 |

关键状态由普通 C# 数据结构保存，Unity 对象读取状态并更新表现。模拟入口按固定 Tick 接收输入并产生新状态。当前使用浮点数，状态回放用于发现架构问题和验证相同运行环境中的一致性。

## 服务器建设顺序

1. 先让单机玩法模拟和回合状态机独立运行，服务器只承载状态和规则，不承载客户端表现。
2. 再建立连接管理、玩家映射、输入接收、Tick 推进和快照发送。
3. 协议先覆盖加入、离开、输入、状态快照、回合开始、结算和重开。
4. 双客户端能够稳定完成整局后，再实现远端插值和本地预测。
5. 弱网模拟、指标面板和断线处理放在同步流程稳定之后。

服务器构建使用无图形 Unity Server Build。服务器不创建玩家表现对象，不读取本地输入，不直接依赖场景表现脚本。客户端和服务端共享协议定义，协议变更时同步检查两端。

## 阶段闸门

### 第一阶段：可玩单机闭环

完成场地、移动、跳跃、冲刺、推挤、掉落、复活、计分、胜负、重开和机器人。单机能够连续完成多局，流程没有阻断，操作结果可以解释。

### 第二阶段：展示质量

完成输入缓冲、空中控制、命中反馈、镜头、动画、音效和基础 UI。录制一段能够展示玩法的短视频，README 说明目标、结构、运行方式和关键取舍。

### 第三阶段：稳定联机

完成状态分离、固定 Tick、双客户端连接、输入传输、服务器权威模拟、状态快照和远端插值。两个客户端能够稳定完成整局，胜负结果一致。

### 第四阶段：网络深度

在前三阶段稳定后加入本地预测、服务器校正、延迟丢包模拟和指标面板。每项扩展都必须有可运行的验证场景和可以说明的结果。

## 测试与验收

1. 单机连续完成 10 局，机器人能够稳定参与完整回合。
2. 回放 3 局完整输入，末尾状态能够保持一致。
3. 双客户端连续完成多局，加入、开始、结算、重开和离开流程正常。
4. 在延迟、抖动和丢包环境中观察远端插值、本地预测和服务器校正结果。
5. Server Build 与客户端构建能够从干净目录运行。
6. 视频、README、架构图和简历项目描述与实际完成内容一致。

## 投入管理

每周复盘一次，只记录当前已经完成的内容、下一阶段唯一主要交付和需要缩减的内容。

求职期间的优先级为：投递与面试准备、算法与八股、已有项目讲解、物理派对阶段目标、额外技术探索。

如果单机闭环尚未完成，项目只推进玩法和表现；如果展示材料尚未完成，项目只推进打磨和文档；如果双客户端尚未稳定，项目只推进同步基础；本地预测和指标放在稳定同步之后。

## 当前执行顺序

1. 冻结玩法规格并搭建工程基线。
2. 完成回合状态机、角色移动、跳跃、掉落和重开。
3. 完成推挤、冲刺、计分、胜负、机器人和单机验收。
4. 完成手感、镜头、动画、音效、视频、README 和架构图。
5. 抽取状态模型并接入固定 Tick。
6. 再实现服务器循环、协议、快照同步和远端插值。
7. 双客户端稳定后，再实现本地预测、校正、弱网模拟和指标。

当前第一项工作是冻结玩法规格。规格定稿后立即搭建工程基线并实现回合骨架。
