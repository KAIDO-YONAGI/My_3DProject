## 0. 三十秒速查

| 我要做的事 | 用什么 | 关键约束 |
|---|---|---|
| 同步本地算出来的连续状态（速度、朝向、状态位） | 在**同一个网络对象**上加 `syncDirection = ClientToServer` 的 `NetworkBehaviour`，里面放 `[SyncVar]` 或自己写 `OnSerialize` | 服务器校验对象归属后转发；**不需要 Command，不额外多一个 RTT** |
| 同步服务器决定的状态（血量、分数、规则判定） | 服务器写 `[SyncVar]`（默认 `ServerToClient`） | 客户端写会被服务器拒绝，甚至断线 |
| 一次性事件（起跳、落地、爆炸、受击、表情） | `[Command]` 上行、`[ClientRpc]`/`[TargetRpc]` 下行 | 不要用它传每帧连续量 |
| 高频物体轨迹（投掷物） | `NetworkRigidbodyUnreliable` / `NetworkTransformUnreliable`（非可靠通道） | 别用 Reliable，会队头阻塞 |
| 权威裁决"谁被炸、被推多远" | 服务器计算，`[TargetRpc]` 发回该角色的拥有者执行 | 角色仍是客户端权威，服务器写位置无效 |
| 让"到时间炸"的特效对上位置 | 服务器用 `NetworkTime.time` 记时刻，事件带服务器时间戳 | 客户端按自己的时间轴对齐，别按收到消息的瞬间播 |
| 新增网络预制体 | 注册进 `NetworkManager.spawnPrefabs` | 组件/同步字段一变，客户端与服务器必须一起重新构建 |

## 2. 状态同步的四条通道

### 2.1 SyncVar / SyncList：谁能写

判定逻辑在 `Assets/Plugins/Mirror/Core/NetworkBehaviour.cs:290-363`（`InitSyncObject` 里的 `IsWritable` 与 `IsRecording`）：

| 模式 | 客户端能否写 SyncVar / SyncList |
|---|---|
| `ClientToServer` 且 `isOwned` | **可以**：本地写值 → 服务器校验归属后接收 → 转发给其他观察者 |
| `ClientToServer` 非 owner | 不可以（不会进入序列化） |
| `ServerToClient`（默认） | 只能服务器写；客户端写不会生效，尝试发送会被服务器拒绝 |

关键结论：**同步方向是"整个 behaviour"级别的属性**（`[HideInInspector] public SyncDirection syncDirection`，`NetworkBehaviour.cs:37`），不是单个字段级别。

服务器端校验在 `Assets/Plugins/Mirror/Core/NetworkServer.cs:419`（`OnEntityStateMessage`）：netId 有效 **且** `identity.connectionToClient == connection` 才执行 `DeserializeServer`；失败时按 `exceptionsDisconnect` 决定是否断线。源码注释原话是"an attacker may attempt to modify a not-owned or not-ClientToServer component"。

`[SyncVar]` 与自定义序列化的取舍：

| | `[SyncVar]` | 自定义 `OnSerialize`/`OnDeserialize` |
|---|---|---|
| 写法 | 加特性即可 | 自己写打包与解包 |
| 变化才发 | 自动（脏位） | 自己实现 |
| 后加入玩家拿初值 | 自动（Spawn 时服务器序列化当前值） | 自己处理 `initialState` 语义 |
| 带宽/精度 | 按字段类型原样发 | 可自行量化（bit 打包） |
| 适合 | 低频离散量（枚举、布尔、血量） | 每帧都变的连续量（速度、朝向、进度） |

### 2.2 Command：客户端 → 服务器

- 定义：`[Command]`（`Assets/Plugins/Mirror/Core/Attributes.cs:25`）。
- 服务器校验：`NetworkServer.cs:393-407`，`requiresAuthority` 为真时要求 `identity.connectionToClient == conn`，否则只记警告不执行。
- 用法要点：需要对象归属；默认走可靠通道；**不要用它传每帧连续量**。

### 2.3 RPC：服务器 → 客户端

- `[ClientRpc]`（`Attributes.cs:35`）广播给所有观察者；`[TargetRpc]`（`Attributes.cs:45`）发给指定连接。
- 用于一次性事件：爆炸表现、受击反馈、音效触发。
- 现有项目里 `characterId` 用的是 **Command + SyncVar** 组合，见 `Assets/Core/Scripts/Networking/NetworkCharacterSync.cs`：`[SyncVar(hook = nameof(OnCharacterIdChanged))] private int characterId`（`:20-21`）、`[Command] CommandSetCharacter(int)`（`:92`）、`OnCharacterIdChanged`（`:106`）、`ApplyCharacter`（`:111`）。

### 2.4 自定义序列化：跟位置同一个包

范例就是 `Assets/Plugins/Mirror/Components/NetworkTransform/NetworkTransformReliable.cs`：`OnSerialize`（`:217`）、`OnDeserialize`（`:291`，`:337` 按 `isServer`/`isClient` 分流）。

打包规则（源码注释，`NetworkServer.cs` 不可靠 delta 处理分支）：**每个 Entity 一条 `EntityStateMessage`**，所以同一个对象上的多个 `NetworkBehaviour` 是合在一个包里的。这决定了"新状态加在同一个对象上"比"新建网络对象"更省带宽、时序也更一致。

## 3. 现有移动链路（端到端）

### 3.1 本地：输入 → 运动 → 动画

`PlayerCharacterController.Update()`（`Assets/Core/Scripts/Character/Runtime/PlayerCharacterController.cs:59-84`）里有两道闸门：

- `:63-66` **专用服务器直接 return**（注释理由：服务器没有输入和相机，继续跑会把网络玩家推出场景）。
- `:69-72` 非本地玩家直接 return。

通过闸门后：`ReadInput()` → `motor.Tick(input, inputSpace, Time.deltaTime)` → `animationDriver?.Apply(motion)`（`:81-83`）。

运动计算全在 `CharacterMotor.Tick`（`Assets/Core/Scripts/Character/Runtime/CharacterMotor.cs:33-98`）：

- 输入方向解析 `:38`、可选转向 `:39-42`；
- 起跳读移动前的贴地状态 `:45-55`；
- 水平速度按加/减速逼近目标 `:58-67`，重力 `:68`；
- **`characterController.Move(frameMotion)`（`:71`）是位置的唯一来源**；
- 落地判定用移动后的碰撞结果 `:80`，贴地时用 `GroundedPull` 保持吸附 `:81-84`；
- 动画权重直接取输入幅度（`:92`），所以松键当帧就回 Idle。

### 3.2 上行：ClientToServer 状态

根对象的 `NetworkTransformReliable`：

- `UpdateClient()`（`NetworkTransformReliable.cs:139`）里只有 `IsClientWithAuthority` 才写（`:143`、`:158`）；
- 变化判定 `Changed()`（`:192`）/ `QuantizedChanged()`（`:207`）；
- 位置变化最终变成可靠通道上的 `EntityStateMessage`。

### 3.3 服务器：校验 + 转发，不模拟

`NetworkServer.OnEntityStateMessage`（`NetworkServer.cs:419`）校验归属后调用 `DeserializeServer`，进入 `OnClientToServerSync`（`NetworkTransformReliable.cs:348`）**只写入服务器副本，不模拟角色**；随后由服务器转发给其他观察者。

### 3.4 远端：插值 → 由位移反推动画

- 客户端 `NetworkClient.OnEntityStateMessage`（`NetworkClient.cs:1493`）→ `OnServerToClientSync`（`NetworkTransformReliable.cs:379`），其中 `:382` 对 `IsClientWithAuthority` 直接 return——**拥有者不回读服务器值**，这是本地手感不抖的关键。
- 快照缓冲与插值：`AddSnapshot`（`NetworkTransformBase.cs:231`）、`Apply`（`:271`）。
- 动画在 `LateUpdate()` 里做（`PlayerCharacterController.cs:86-97`，`:90` 判定远端），`ApplyRemoteAnimation`（`:216-255`）按顺序：
  1. `(当前位置 - 上一帧位置) / deltaTime` 得到帧速度（首帧或 delta 异常时只记位置并给 Idle 快照）；
  2. 水平投影 + `InverseTransformDirection` 得到本地方向与 `speed`；
  3. 冲刺阈值 `Mathf.Lerp(runSpeed, sprintSpeed, 0.65f)`；
  4. `grounded = characterController.isGrounded || |frameVelocity.y| < 0.05`；
  5. `locomotionWeight = speed / runSpeed`；
  6. 组 `CharacterMotion` 交给 `CharacterAnimator.Apply`（`CharacterAnimator.cs:119-140`）。
- `CharacterAnimator`：落身边沿重置为纯 Idle（`:127-131`、`:205-212`），否则写 `MoveX`/`MoveY` 并按权重混合 Idle/Run/Sprint（`:217-242`）；**跳跃与下落只由一个 `Grounded` 布尔驱动**（`:137-138`）。

### 3.5 本地与远端的差异

| 项 | 本地 | 远端（反推） |
|---|---|---|
| `LocomotionWeight01` | 输入幅度（松键当帧回 Idle） | `speed / runSpeed`（停步滞后） |
| `WantsSprint` | 冲刺键 + 有输入 | 速度超过 `Lerp(run, sprint, 0.65)` 猜的（被撞飞可能误判冲刺） |
| `IsGrounded` | 移动后的碰撞结果 | `isGrounded \|\| |vy| < 0.05` 启发式 |
| 典型问题 | — | 上台阶/下坡/平台抖动会闪跳或闪落；插值抖动会污染速度估计 |

结论：远端看起来不对时，先查快照与插值，再查模型；需要更准时，同步一两个 bit 的"意图"比上 IK 划算。

## 4. tick 与时间

### 4.1 发送节拍参数

| 项 | 位置 | 值 |
|---|---|---|
| `NetworkServer.tickRate` | `NetworkServer.cs:39` | 默认 `60` |
| `NetworkServer.tickInterval` | `NetworkServer.cs:47` | `1 / tickRate` ≈ 16.7 ms |
| `NetworkServer.sendRate` | `NetworkServer.cs:53` | `=> tickRate`（别名） |
| `NetworkServer.sendInterval` | `NetworkServer.cs:54` | `=> 1 / sendRate` |
| `NetworkManager.sendRate` | `NetworkManager.cs:43-44` | 工程里 `60` |
| `Application.targetFrameRate` | `NetworkManager.cs:689` | `= sendRate` |

`NetworkManager.ApplyConfiguration()`（`NetworkManager.cs:289` 起，**每帧调用**）把工程配置写进运行时：`NetworkServer.tickRate = sendRate`（`:292`），以及 `unreliableBaselineRate`、`unreliableRedundancy`、`NetworkClient.snapshotSettings`、`connectionQualityInterval`。注释说明这是为了"避免两个事实来源"。

### 4.2 节拍怎么推进（核心算法）

`NetworkLateUpdate`（在一帧所有 `Update`/`FixedUpdate`/`LateUpdate` 之后）用 `AccurateInterval.Elapsed` 判断是否到了下一个节拍，实现见 `Assets/Plugins/Mirror/Core/Tools/AccurateInterval.cs:33-84`：

```csharp
if (time < lastTime + interval) return false;

// 朴素写法，会丢掉不足一个 interval 的余数：30 Hz 实测只跑到 18-19 Hz
// lastTime = time;

// 精确但卡顿后会连发补帧：
// lastTime += interval;

long multiplier = (long)(time / interval);
lastTime = multiplier * interval;   // 量化到 interval 的整数倍
return true;
```

要点：节拍不是定时器线程打出来的，而是**每帧比时间、到点推进**，推进点永远落在节拍的整数倍上，既不漂移也不在卡顿后连发。

### 4.3 一个节拍里做了什么

`Broadcast()`（`NetworkServer.cs:2241`）对每个 ready 连接依次做三件事：

1. 发 `TimeSnapshotMessage`（不可靠通道，`:2275`）——客户端拿它对时；
2. `BroadcastToConnection`（`:2118`、调用点 `:2278`）——广播该连接观察到的实体状态；
3. `connection.Update()`（`:2282`）——把这一节拍攒下的消息刷给传输层。

### 4.4 批量打包与时间戳

`Assets/Plugins/Mirror/Core/NetworkConnection.cs`：

- 每个连接、每个通道一个 `Batcher`（`:48`、`GetBatchForChannelId` `:68`）；
- 消息进包时带上 `NetworkTime.localTime` 时间戳（`:137`）；
- 接收端读包头时间戳作为整包时间：`remoteTimeStamp`（`:57`）；
- 刷包在 `Update()`（`:144-170`）；
- 注释（`:126-136`）明确"我们永远批量发送，不是可选项"，原因是接收端 `NetworkTransform` 之类依赖时间戳。

### 4.5 不可靠通道的 tick 语义

- 服务器序列化不可靠组件时传入的 tick **就是 Unity 帧号**：`GetServerSerializationAtTick(Time.frameCount, ...)`（调用点 `NetworkServer.cs:2050`、`:2083`；实现 `NetworkIdentity.cs:1446`，注释"每个 tick 只重建一次序列化，其余复用"）。
- 幂等靠两个东西：delta 消息带 `baselineTick`（旧 baseline 直接丢弃）、`NetworkIdentity.lastUnreliableStateTime`（`:250`，乱序与重复按时间戳忽略）。
- `unreliableBaselineRate`（被 clamp 在 `1..sendRate`，`NetworkManager.cs:182`）周期性补发可靠基线，对应 `NetworkServer` 里的 `unreliableFullSendIntervalElapsed`。

### 4.6 客户端时间轴

`Assets/Plugins/Mirror/Core/NetworkTime.cs`：

| 成员 | 行为 |
|---|---|
| `time`（`:74`） | 服务器上 = `localScaledTime`（`Time.timeAsDouble`，`:45`）；客户端 = `NetworkClient.localTimeline`（快照插值时间轴） |
| `localTime`（`:35`） | `Time.unscaledTimeAsDouble`，不受 `timeScale` 影响 |
| `PingInterval`（`:22-23`） | 默认 `0.1` 秒一次 ping/pong |
| `PingWindowSize`（`:27`） | 50 次滑动平均求 RTT（`OnServerPong` `:244`） |
| `predictedTime` / `rtt` | `:125` / `:140` |
| 插值偏移 | `NetworkTransformBase.timelineOffset`（`:111`）= `sendInterval * sendIntervalMultiplier`（`:79`） |

**实践结论**：服务器广播事件时带服务器时间戳，客户端按自己的时间轴（而不是"收到消息的瞬间"）对齐播放，才能和它正在显示的插值位置吻合。

## 5. 投掷物与爆炸物（Proposal，尚未实现）

当前 `Assets/Core` 下**没有任何投掷物或爆炸相关代码**，连 `Rigidbody` 都没用过（只有 Mirror 自带示例里有）。以下是从零设计的建议。

### 5.1 三种轨迹同步方案

| | 只传发射事件，各端自算 | 投掷者权威 + 服务器转发 | 服务器模拟 + 客户端插值 |
|---|---|---|---|
| 带宽 | 最低（一次事件） | 每节拍快照（非可靠） | 每节拍快照（非可靠） |
| 投掷者手感 | 零延迟 | 零延迟 | 有 RTT（可用本地预测球掩盖） |
| 公平性 | 取决于谁裁决 | 投掷者说了算 | 服务器唯一裁决 |
| 风险 | PhysX 跨机不确定，长时间飞行或中途碰撞会分叉 | 投掷者掉线球冻住；命中可作弊 | 服务器要跑物理；需要下发效果 |
| 适用 | 中途不碰撞、到时间炸 | 朋友局、能接受投掷者裁决 | 需要公平裁决、爆炸影响多人 |

### 5.2 推荐组合（服务器裁决 + 拥有者执行）

1. 投掷者按投掷键 → `[Command]` 上报起点、初速度、道具类型；
2. 服务器校验（冷却、是否持有该道具、起点是否在角色附近）→ `NetworkServer.Spawn` 投掷物并赋初速度；
3. 投掷物在服务器上模拟，用**非可靠**快照同步给观察者（非权威端自动变 kinematic）；
4. 服务器用 `NetworkTime.time` 记引信到点时刻并在自己的节拍里比较；
5. 到点：服务器 `OverlapSphere` 收集受影响角色、算各人冲量 → 广播爆炸事件（位置、半径、力度、时间戳）→ 对每个受影响角色用 `[TargetRpc]` 把冲量发给它的拥有者，由拥有者本人在本地施加；
6. 各端按时间戳播特效与音效。

可选的体验优化：投掷者本地立刻生成一个**不带网络组件**的纯视觉预测球，服务器权威那份状态到达后切换过去。

### 5.3 落地清单

**新增**

- 投掷物预制体：`NetworkIdentity` + `Rigidbody` + `NetworkRigidbodyUnreliable` + 自己的引信脚本（只在服务器跑）。
- 注册进 `NetworkManager.spawnPrefabs`（当前 0 项，需手动加）。
- 投掷的 `[Command]` 与服务器校验逻辑。
- 爆炸事件 RPC 与特效触发。

**需要改现有代码（三处）**

- `CharacterMotor` 增加外部冲量入口（现在没有）；
- `CharacterMotion` 增加"被击退/眩晕"之类状态字段，`CharacterAnimator` 增加对应参数与过渡（否则远端动画仍是跑走跳，因为该状态推不出来）；
- 接收 `[TargetRpc]` 的执行路径：服务器算出的冲量交回拥有者，由拥有者在自己的 `CharacterMotor` 上施加。

**每处都要注意的坑**

- `CharacterMotor` 的三个坑：没有输入时目标速度为零，`Vector3.MoveTowards`（`CharacterMotor.cs:67`）会按 `Deceleration` 把冲量拉回来；贴地时 `verticalVelocity` 会被 `GroundedPull` 每帧重置（`:81-84`），向上击飞必须在离地那一帧才生效；`OrientToMovement` 会让角色转向移动方向（`:39-42`、`RotateTowards` `:134-138`），被炸飞时通常要临时抑制或改用冲量方向。
- 服务器手上角色的位置是客户端上报的，**比真实位置晚约一个 RTT**，半径边缘的判定会有误差；可以用两次快照差分估速度做外推补偿，或接受误差。
- 角色是客户端权威时，服务器直接写位置无效（下一帧会被拥有者上报冲掉），所以效果必须回到拥有者执行。要让服务器真正接管，就得连同角色移动权威一起改成服务器模拟 + 预测/和解。

### 5.4 组件与通道的实测细节

- `NetworkRigidbodyUnreliable : NetworkTransformUnreliable`、`NetworkRigidbodyReliable : NetworkTransformReliable`，两者都有 `clientAuthority => syncDirection == SyncDirection.ClientToServer`（`Assets/Plugins/Mirror/Components/NetworkRigidbody/NetworkRigidbodyUnreliable.cs:7`、`:9`）。
- 非权威端会被强制设为 kinematic：`if (!owned) rb.isKinematic = true;`（`NetworkRigidbodyUnreliable.cs:73`、`:85`、`:96`）→ 不会两边物理打架。
- 命名陷阱：`NetworkRigidbodyUnreliableCompressed.cs` 文件里实际的类名是 **`NetworkRigidbodyHybridCORE : NetworkTransformHybrid`**，在 Add Component 里搜 `UnreliableCompressed` 找不到。
- 通道选择：高速物体走非可靠；可靠通道有队头阻塞，一次丢包会让后续快照排队等重传，表现是顿一下再瞬移。
- 兼容性：新增预制体或改动同步字段后，客户端与服务器必须一起重新构建部署（`Protocol/Protocol_Guide.md:33-52`）。

## 8. 待确认事项（决定后续方案走向）

1. **权威范围**：只让投掷物与爆炸裁决走服务器（改动小，推荐起步），还是把角色运动也改成服务器权威（架构级，需输入上行 + 预测/和解，量级数周）。
2. **要同步的状态清单**：每项按四条标准分类——谁决定（自己算 / 服务器定）、多久变一次（每帧 / 偶尔 / 一次）、丢了能否接受、新玩家进场是否必须立刻看到。据此归入"跟位置同包""`[SyncVar]`""一次性 RPC"三类。
3. **投掷物行为**：到时间炸已确认；是否中途弹跳/滚动、是否会连锁引爆或被推动，决定能否用"只传发射事件"这种零带宽方案。
4. **需要被同步的离散状态**：被击退、眩晕、持物、倒地等远端推不出来的状态，需要新增字段并同步。
