# 网络同步速查手册

这份手册查两件事：Mirror 的各种同步机制分别用在什么场合，以及本项目现在的同步结构长什么样。写法是先讲清机制和取舍，再用表格汇总可以直接对照的结论。事实基准是 2026-10-10 的工作区状态（Mirror 96.11.2、Unity 2022.3.62f3c1）；角色运动那部分当时正由另一个会话重构，读到不一致时以代码为准。项目权威文档在 `Y_MultipleAgentWorkflow/` 下，这份只是参考手册。

## 一、数据语义决定链路

选机制不是挑 API，而是先给数据定性：这个值**谁决定**（自己算还是服务器定）、**多久变一次**（每帧、偶尔、一辈子一次）、**丢了能不能忍**、**新来的玩家要不要立刻看到**。四问答完基本就定了：

| 数据语义 | 用什么 | 方向 | 适合的场景 |
|---|---|---|---|
| 请求执行操作 | `[Command]` | 客户端 → 服务器 | 按键要求服务器做事，且服务器必须校验 |
| 持续存在的状态 | `[SyncVar]` | 服务器 → 客户端；组件设为 ClientToServer 时拥有者可写 | 血量、角色编号、比赛模式这类低频事实 |
| 持续存在的集合 | `SyncList`、`SyncDictionary`、`SyncHashSet`、`SyncSortedSet` | 同上 | 背包、名单、道具表 |
| 一次性公共事件 | `[ClientRpc]` | 服务器 → 该对象的观察者 | 爆炸表现、受击反馈、音效触发 |
| 一次性定向通知 | `[TargetRpc]` | 服务器 → 指定客户端 | 只给某个玩家发奖励、发冲量 |
| 与对象无关的消息 | `NetworkMessage` | 双向，按连接 | 登录、大厅、聊天、时间同步 |
| 连续的位置与旋转 | `NetworkTransform` 系列 | 两种方向都支持 | 角色、投掷物、可推动物体 |

有两条经验值得记住。一是**状态类的东西优先挂在同一个网络对象上**，因为同一对象上的多个同步组件会合进同一个状态包，比另起一个网络对象既省带宽、时序也更一致。二是**事件不要当状态用**：用 RPC 发一次爆炸是对的，同步一个"正在爆炸"的布尔每帧翻转是错的；反过来，把持续状态写成 RPC 也一样糟——晚加入的玩家收不到，状态就永久缺失。

## 二、两条所有通道都要遵守的规则

**写权限按组件定，不按字段定。** 每个 `NetworkBehaviour` 只有一个同步方向，ServerToClient 时只有服务器能写，ClientToServer 且对象属于你时拥有者能写。服务器收到客户端上报的状态时会校验这个对象是否真的属于该连接，不通过就丢弃，`exceptionsDisconnect` 打开时还会直接断线。

| 组件方向 | 谁能写 | 说明 |
|---|---|---|
| ServerToClient | 只有服务器 | 客户端写无效；试图发送会被服务器拒绝 |
| ClientToServer | 拥有者那一端 | 服务器校验归属后转发给其他人，不需要 `[Command]`，也不额外多一个 RTT |

所以"同一个组件里一部分字段服务器写、一部分客户端写"是做不到的，要分方向就得拆成两个组件（本项目就是这么做的，见第三节）。运行时改方向也很危险：两端不一致会直接报权限错误。

**所有通道共用同一套批量发送。** Command、RPC、SyncVar 的增量、位置快照，最后都进每条连接、每个通道的批量缓冲，进包时带上时间戳，等下一个发送节拍才一起发出去。发送率是 60，所以任何通道最快也要等约 16.7 毫秒；批量不是可选项，因为接收端的插值依赖包头时间戳。任何"每帧都发一次"的用法在这一层就会变成带宽和延迟问题。

## 三、项目现在的同步结构

网络玩家是一个**只有根节点、没有子物体**的预制体：可视角色在运行时按编号实例化后挂上去，挂上去之后它自己那份玩家控制器和碰撞控制器会被禁用，所以全场只有根节点在模拟运动、也只有根节点在同步。

| 根上的组件 | 方向 | 同步内容 | 写入方 |
|---|---|---|---|
| `NetworkTransformReliable` | ClientToServer | 位置与旋转（不同步缩放） | 拥有者客户端 |
| `NetworkCharacterSync` | ServerToClient | 角色编号 `characterId` | 服务器 |
| ~~`NetworkCharacterMovementSync`~~ | ClientToServer | 运动表现状态：离散状态 + 本地方向 + 权重 | 拥有者客户端 |

> **勘误（2026-10-10）**：上表最后一行的运动同步组件**尚未实现**，`NetworkCharacterMovementSync.cs` 在磁盘上不存在。`NetworkPlayer.prefab` 上曾残留一条指向它的组件记录（GUID `0b9dca0ce9ed4d9094a8df5c8901df22`，Missing Script），已于当日清理。本节第四小节对该组件的描述属于**设计方案**，不是当前实现；当前远程动画固定回退到 Idle。权威边界见 `Y_MultipleAgentWorkflow/Multiplayer/Sync_Protocol.md` 的 Proposal 一节。

另外根上还有基础的 `Transform`、`NetworkIdentity` 和 `CharacterController`（高 2、半径 0.5、中心抬高 1 米、坡度上限 45 度、台阶补偿 0.3）。两根同步链路方向刚好相反是刻意的：**编号由服务器说了算，运动表现由拥有者说了算**。角色脚本按职责分层放在动画、控制、输入、运动、表现几个目录下，动画素材用覆盖器把通用模板的占位片段换成各角色自己的素材，四个角色的模型都是有效 Humanoid。

位置同步的具体配置：

| 配置 | 值 | 含义 |
|---|---|---|
| 方向 | ClientToServer | 客户端权威，服务器只转发 |
| `syncInterval` | 0 | 每个发送节拍都参与打包 |
| `onlySyncOnChange` | True | 变了才发，静止时不上报 |
| 位置量化精度 | 0.01 | 约 1 厘米，小于该变化不发 |
| 旋转敏感度 | 0.01 | 旋转超过该变化才算变化 |
| 压缩旋转 | True | 旋转按最小编码发送 |
| 插值 | 全开 | 接收端按时间轴插值位置、旋转、缩放 |
| 坐标空间 | Local | 相对父对象 |
| 插值延迟 | True | 故意延后一个发送间隔，抗抖动 |
| 更新时机 | Update | 与帧同步采集 |

NetworkManager 侧的关键配置：

| 配置 | 值 | 含义 |
|---|---|---|
| `sendRate` | 60 | 同时决定 tick 节拍与目标帧率 |
| `unreliableRedundancy` | False | 不重复发不可靠包 |
| `exceptionsDisconnect` | True | 反序列化异常直接断线 |
| `spawnPrefabs` | 空 | 新增网络预制体必须手动登记（玩家预制体会被自动排除） |

## 四、移动链路：从输入到远端表现

**本地这一段**：控制器先过两道闸门——专用服务器直接返回（服务器没有相机和输入，继续跑会把网络玩家推落场景），联机时非本地玩家也返回。过关后是"读输入 → 运动计算 → 应用动画 → 提交网络快照"的固定顺序。运动计算负责把输入方向换算成世界方向、按加/减速逼近目标速度、处理跳跃与重力，最后交给 CharacterController 执行位移；之后用**移动后的碰撞结果**判定落地，这样离地当帧就进入跳跃、接触地面当帧就回到地面。动画权重直接取输入幅度，所以松手当帧就回 Idle。

**上行有两条并行链路**（其中第二条尚未实现，见上方勘误）：位置仍由 `NetworkTransformReliable` 从根对象采集，只有拥有者会写；运动表现状态计划由新的 `NetworkCharacterMovementSync` 承担，拥有者每帧提交一次快照，即使角色静止也持续标脏，避免远端缓冲断档。快照内容就三样：离散运动状态（1 字节）、角色自身坐标系的移动方向（二维向量）、移动权重（浮点）。三个字段都做过范围校验，方向长度、权重范围、枚举合法性任何一项不合法就丢弃。

**服务器**（以下为计划，尚未实现）只校验归属与转发，不模拟角色运动。对运动状态它计划多做一件事：收到拥有者的快照后按远端时间戳加一个发送间隔插入缓冲，再按该连接的时间轴采样插值，把结果作为自己广播的源——所以其他观察者看到的不是原始快照，而是经过服务器平滑后的状态。

**远端**在 `LateUpdate` 里取动画。当前实现只有 Idle 回退这一半：`PlayerCharacterController.ApplyRemoteAnimation` 直接应用 Idle。计划是问运动同步组件要一个"按网络时间采样的当前状态"，拿到就应用，拿不到（延迟装配或第一个快照还没到）才回退到 Idle。位置由变换同步的插值结果驱动，运动同步接入后两者互不干扰。

| 环节 | 本地玩家 | 远端玩家 |
|---|---|---|
| 输入 | 读本地输入 | 完全不读输入 |
| 位移 | CharacterController 驱动根对象 | 由位置快照插值得到 |
| 动画四项来源 | 输入幅度、冲刺键、移动后的碰撞结果 | 当前恒为 Idle；计划改为网络同步来的状态、方向、权重，按网络时间插值 |
| 驱动时机 | `Update` 内一帧走完 | `LateUpdate`；当前不读快照，计划读已采样的快照 |
| 未就绪时 | — | 回退 Idle（当前即此状态） |

这次改造**计划**解决的老问题：以前远端动画靠帧位移反推，上台阶、下坡、平台边缘会闪跳或闪落，被撞飞或被爆炸加速会被误判成冲刺，松手还会滞后；改造后这些量由拥有者直接同步，猜的成分没有了。代价是每个快照多十几个字节，但因为和位置合在同一个状态包里，不额外多一个 RTT。仍然要注意两点：离散状态在插值时是二选一（插值过半才切到下一个状态），所以极短的状态可能在两个快照之间被跳过；快照没到达前必须有明确的回退，否则远端会僵在最后一帧。

## 五、tick 与时间

| 参数 | 值 | 说明 |
|---|---|---|
| `tickRate` | 默认 60 | 服务器逻辑节拍 |
| `tickInterval` | 1/60 ≈ 16.7 毫秒 | 节拍间隔，`tickRate` 的倒数 |
| `sendRate` | 工程里 60 | 每帧写进 `tickRate`，同时作为目标帧率，避免两个事实来源 |
| `sendInterval` | 1/60 | 与发送率同义，时间快照与插值偏移都基于它 |
| `unreliableBaselineRate` | 1 到 `sendRate` | 不可靠通道周期性补发可靠基线 |

节拍的推进不在定时器线程里，而是每帧比时间、到点推进，推进点永远落在节拍的整数倍上：

```csharp
if (time < lastTime + interval) return false;

// 朴素写法会丢掉不足一个 interval 的余数：30 Hz 实测只跑到 18-19 Hz
// lastTime = time;

// 精确，但卡顿之后会连发补帧：
// lastTime += interval;

long multiplier = (long)(time / interval);
lastTime = multiplier * interval;   // 量化到 interval 的整数倍
return true;
```

一个节拍里做的事按顺序是三步：

| 步骤 | 内容 | 通道 |
|---|---|---|
| 1 | 给每个就绪连接发一条时间快照，供客户端对时 | 不可靠 |
| 2 | 广播该连接能看到的所有实体状态 | 各通道批量 |
| 3 | 把这一拍攒下的消息刷给传输层 | — |

不可靠通道有两个细节值得记：服务器序列化时用的"tick"就是 Unity 帧号（每个 tick 只重建一次序列化，其余复用），所以没有独立的网络 tick 编号；幂等靠每条增量消息里的基线编号（旧基线直接丢弃）和时间戳（乱序与重复忽略）来保证。

客户端的时间轴由时间快照插值而来，服务器上是 `Time.timeAsDouble`，两端每 0.1 秒交换一次 ping/pong，RTT 取 50 次滑动平均。实践结论：**服务器广播事件要带服务器时间戳，客户端按自己的时间轴对齐播放**，而不是收到就播，这样才能和它正在显示的插值位置吻合。

## 六、投掷物与爆炸物（还没实现，以下都是设计建议）

项目里目前没有任何投掷物或爆炸相关代码，连 `Rigidbody` 都没用过。三种做法各有取舍：

| 方案 | 带宽 | 投掷者手感 | 公平性 | 风险 |
|---|---|---|---|---|
| 只传发射事件，各端自算 | 最低（一次事件） | 零延迟 | 取决于谁裁决 | 物理不确定，中途碰撞或长飞会分叉 |
| 投掷者权威 + 服务器转发 | 每节拍快照 | 零延迟 | 差，命中可作弊 | 掉线球冻住 |
| 服务器模拟 + 客户端插值 | 每节拍快照 | 有 RTT | 唯一裁决，最公平 | 服务器要跑物理，需下发效果 |

派对游戏建议第三种为主，投掷者本地另放一个不带网络组件的纯视觉预测球来掩盖延迟。推荐时序：

1. 投掷键触发 `[Command]`，上报起点、初速度、道具类型；
2. 服务器校验冷却、是否持有该道具、起点是否贴着角色；
3. 通过后由服务器生成投掷物并赋初速度，挂刚体与不可靠同步组件；
4. 投掷物只在服务器模拟，用不可靠快照同步给观察者（非权威端会被强制变 kinematic，不会两边打架）；
5. 服务器用自己的网络时间记下引信到点时刻，在自己的节拍里比较；
6. 到点广播爆炸事件（位置、半径、力度、服务器时间戳），供各端按自己的时间轴播特效；
7. 对每个受影响角色用 `[TargetRpc]` 把冲量发给它的拥有者，由拥有者本人在本地施加。

需要动的现有代码只有三处，但每处都有坑：

- **运动控制器需要一个外部冲量入口。** 三个坑：没有输入时目标速度为零，减速逻辑会把冲量拉回来；贴地时竖直速度每帧被贴地拉力重置，向上击飞必须落在离地那一帧；角色会自动转向移动方向，被炸飞时要临时抑制或改成朝冲量方向。
- **运动状态需要新增一个"被击退/眩晕"。** 运动快照现在传的是离散状态，加状态值比加布尔字段更自然，但动画驱动必须认识这个新状态，否则远端仍然只会跑走跳。
- **冲量要回到拥有者执行。** 角色是客户端权威，服务器直接写位置下一帧就会被拥有者上报冲掉；服务器算裁决、拥有者做表现，才是当前架构下的正确分工。要让服务器真正接管角色运动，就得连移动权威一起改成服务器模拟加预测和解，那是数周量级的改造。

另外三个现实约束：服务器手上的角色位置是客户端上报的，比真实位置晚大约一个 RTT，半径边缘的判定会有误差（可以用两次快照差分估速度外推，或接受误差）；投掷物这类高速物体一定走不可靠通道，可靠通道有队头阻塞，一次丢包会让后续快照排队等重传，表现是顿一下再瞬移；新增网络预制体要登记进 `spawnPrefabs`，改动同步字段后客户端与服务器必须一起重新构建部署。

## 七、各特性的代码写法

| 特性 | 谁调用、谁执行 | 可选参数 | 要记住的 |
|---|---|---|---|
| `[Command]` | 客户端调用，服务器执行 | `channel`、`requiresAuthority` | 需要对象归属；参数必须可序列化；没有返回值 |
| `[ClientRpc]` | 服务器调用，观察者执行 | `channel`、`includeOwner` | 晚加入的客户端收不到 |
| `[TargetRpc]` | 服务器调用，指定客户端执行 | `channel` | 连接参数可省略，省略即发给拥有者 |
| `[SyncVar]` | 由组件方向决定写入方 | `hook` | 值变化才发；hook 只在接收端触发 |
| `SyncList` 等集合 | 同上 | — | 字段声明为 `readonly`，实例不能整体替换 |
| `NetworkMessage` | 双向，按连接 | `requireAuthentication` | 与对象无关，绕过观察者管理 |
| `NetworkTransform` 系列 | 组件字段，不是特性 | 方向、间隔、精度 | 运行时不要改方向 |

```csharp
[Command]                                            // 客户端 → 服务器
void CommandSetCharacter(int requestedCharacterId)   // 方法名带不带 Cmd 前缀都行
{
    // 只在服务器执行，参数与归属都要自己校验
}

[Command(requiresAuthority = false)]                 // 允许在非归属对象上调用
void CmdInteract() { }

[Command(channel = Channels.Unreliable)]             // 默认走可靠通道
void CmdAim(Vector2 aim) { }
```

```csharp
[SyncVar] public int score;                                            // 服务器写，所有客户端收

[SyncVar(hook = nameof(OnHealthChanged))] private int health = 100;    // hook 形参必须是 (旧值, 新值)
void OnHealthChanged(int oldValue, int newValue) { healthBar.value = newValue / 100f; }

[SyncVar] public NetworkIdentity carriedItem;                          // 引用类型也能同步
```

`[SyncVar]` 只能标字段、不能标属性；hook 只在接收端触发，改值那一端要自己刷 UI；每个 behaviour 最多 64 个；初值写在字段上，服务器生成对象时按当前值下发。

```csharp
public readonly SyncList<Item> items = new SyncList<Item>();
public readonly SyncDictionary<int, int> ammo = new SyncDictionary<int, int>();

items.OnChange += (op, index, value) => { };      // 每个操作一个委托：增/插/改/删/清空
items.Callback += OnItemsChanged;                 // 另一个回调同时给出旧值与新值
ammo.OnChange  += (op, key, value) => { };        // 字典是 (操作, 键, 值)
```

集合的变更不会立刻发，要等对象下一次序列化，也就是下一个节拍；后加入的玩家靠生成时的完整状态补齐，不是重放历史变更，所以服务器必须始终是"当前真相"。

```csharp
[ClientRpc]
void RpcPlayExplosion(Vector3 position, float radius) { }

[ClientRpc(includeOwner = false)]        // 拥有者不收
void RpcFlashOthers() { }

[TargetRpc]
void TargetApplyImpulse(Vector3 impulse)      // 省略连接参数 = 只发给拥有者
{
    // 只有这个客户端的这个对象上执行
}
```

```csharp
public struct ChatMessage : NetworkMessage          // 值类型 + 公有字段
{
    public string sender;
    public string text;
}

NetworkServer.RegisterHandler<ChatMessage>(OnServerChat, false);   // 第二参数是是否要求已认证
NetworkClient.RegisterHandler<ChatMessage>(OnClientChat);
NetworkClient.Send(new ChatMessage { sender = "A", text = "hi" });            // 客户端 → 服务器
NetworkServer.SendToAll(new ChatMessage { sender = "S", text = "..." });      // 服务器 → 所有就绪客户端
conn.Send(new ChatMessage { sender = "S", text = "..." }, Channels.Reliable); // 服务器 → 指定连接
```

同族还有几个迟早用上的：`[Server]`、`[ServerCallback]`、`[Client]`、`[ClientCallback]` 控制"只在哪种端执行"（带 Callback 的版本不刷警告，高频回调用它）；`[ShowInInspector]` 让私有集合在 Inspector 里可见；`[ReadOnly]` 把字段置灰；`[Scene]` 把字符串字段变成场景选择器；`[WeaverPriority]` 在同一个类型有多份读写器时指定用哪个。自定义结构体要进 SyncVar、RPC 参数或集合，需要给它写一对扩展方法，方法名按"Write 加类型名"、"Read 加类型名"的约定命名：

```csharp
public static class ItemSerialization
{
    public static void WriteItem(this NetworkWriter writer, Item value) => writer.WriteInt(value.id);
    public static Item ReadItem(this NetworkReader reader) => new Item { id = reader.ReadInt() };
}
```

## 九、还没定的四件事

| 问题 | 影响 |
|---|---|
| 权威范围：只让投掷物与爆炸的裁决走服务器，还是连角色运动也改成服务器权威 | 前者改动小、建议起步；后者是数周量级的预测和解改造 |
| 要同步的状态清单：每项按"谁决定、多久变一次、丢了能否忍、新玩家是否必须立刻看到"分类 | 决定它归属"跟位置同包""SyncVar""一次性 RPC"哪一类 |

| 需要被同步的离散状态：被击退、眩晕、持物、倒地等 | 远端推不出来的状态必须新增字段或状态值并同步 |
