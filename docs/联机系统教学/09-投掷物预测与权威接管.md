# 投掷物预测与权威接管

[返回目录](README.md)

本章把“按下投掷键立即看到球飞出，服务器统一决定运动和命中”接入本项目的网络玩家结构。代码采用扩展练习形式，下面的组件与接口共同描述落地边界。

## 1. 先划分三个对象

| 对象 | 创建位置 | 组件与职责 | 生命周期 |
| --- | --- | --- | --- |
| 玩家上的投掷入口 | 网络玩家 Prefab | `NetworkThrowAbility` 接收本地请求并发送 Command | 跟随玩家 |
| 权威投掷物 | 服务器生成，各观察客户端接收 | `NetworkIdentity`、`NetworkRigidbodyReliable`、`NetworkProjectileState` | 服务器生成与销毁 |
| 预测视觉球 | 投掷者客户端本地生成 | 普通 `MonoBehaviour`、模型与视觉运动 | 本地表现服务管理 |

预测视觉球使用单独的视觉 Prefab。它通过本地 `Instantiate` 创建，运动由轨迹公式或隔离的视觉模拟驱动。碰撞层把它与玩法物理分开，伤害和道具消耗使用服务器结果。

### 纯视觉球的运动代码

下面的组件放在预测视觉 Prefab 上，使用第 08 章的 `BallisticPath`：

```csharp
using Mirror;
using UnityEngine;

public sealed class LocalPredictedProjectile : MonoBehaviour
{
    private Vector3 origin;
    private Vector3 initialVelocity;
    private Vector3 acceleration;
    private double startedAt;
    private bool flying;

    public void Begin(Vector3 start, Vector3 velocity, Vector3 gravity)
    {
        origin = start;
        initialVelocity = velocity;
        acceleration = gravity;
        startedAt = NetworkTime.localTime;
        transform.position = start;
        flying = true;
    }

    private void Update()
    {
        if (flying)
        {
            transform.position = BallisticPath.Evaluate(
                origin, initialVelocity, acceleration,
                NetworkTime.localTime - startedAt);
        }
    }
}
```

本地表现服务在 `BeginPrediction` 中检查本地输入数值，按本地道具配置计算视觉初速度，从手部或本地出手点创建实例，再调用 `Begin`。创建时间使用本地未缩放时间，传入的重力与服务器投掷配置对应。

这个视觉 Prefab 使用模型与上述普通组件，运动采用自由飞行公式。它的创建、匹配、超时与销毁由表现服务统一管理。

权威投掷物使用网络 Prefab，在 NetworkManager 的可生成 Prefab 列表中注册。网络根放刚体、玩法碰撞体和网络组件，模型放在单独的 `Visual` 子节点。快照写网络根，接管过渡写模型子节点。

投掷入口放在 `NetworkPlayer.prefab` 网络根上，与角色切换入口采用相同的归属关系。玩家拥有这个请求入口，投掷物本身交给服务器控制。

## 2. 把原始方案改成规则请求

客户端提供操作意图，服务器根据规则生成发射参数：

| 数据 | 客户端提交 | 服务器如何采用 |
| --- | --- | --- |
| 请求编号 | 每个玩家生命周期内递增 | 去重，并与预测视觉球匹配 |
| 道具编号 | 想使用的道具 | 查询服务器道具配置，校验持有和使用条件 |
| 瞄准方向 | 单位方向或待归一化方向 | 检查数值有效、长度与允许角度，随后归一化 |
| 蓄力比例 | 本地操作得到的比例 | 检查范围，并按服务器配置计算速度 |
| 出手起点 | 本地视觉使用手部位置 | 服务器按接受的玩家位置与规则偏移计算 |
| 最终初速度 | 本地视觉按配置估算 | 服务器按道具、方向和蓄力规则计算 |

这样既保留即时反馈，也让起点、速度、库存和冷却各有明确的决定者。

网络输入属于外部数据。方向检查包含 `NaN`、无穷大、零长度和异常长度，检查通过后再归一化。`NaN` 表示非数值，它会污染后续向量与物理计算。

允许客户端提交起点时，服务器按玩家接受位置、投掷半径、场景阻挡和可达性校验。把任意客户端起点直接用于生成，会让道具出现在规则范围之外。

### 起点如何贴合项目

本项目玩家根的位置采用拥有者客户端上行，服务器接收位置后转发。服务器计算投掷起点时，使用该玩家在服务器上的已接受位置，加上玩法规定的出手偏移。

动画中的手部骨骼适合决定客户端视觉起点。服务器出手位置使用稳定的玩法偏移或服务器维护的姿态数据，角色展示模型与服务器规则分别承担自己的职责。

玩家位置上行与 Command 上行是两条链路。请求到达时服务器持有的位置可能与按键当刻有差距。先限制允许的发射距离并测量误差，需要更精确时在请求中增加输入序号或采样时间，由服务器按定义的位置历史校验。

## 3. 上行、下行与本地预测分别怎么走

```text
投掷者 A 按下投掷键
  → 本地输入把道具、方向、蓄力交给 NetworkThrowAbility
  → 分配 requestId
  → A 创建预测视觉球，立即显示运动
  → A 调用 CommandThrow
  → Mirror 发送请求并在 S 校验玩家对象归属
  → S 执行 CommandThrow 方法体
  → S 校验请求与资源，计算发射参数
  → S 初始化权威投掷物并调用 NetworkServer.Spawn
```

成功后的下行：

```text
S 的 Spawn 提供投掷物身份与初始业务状态
  → A、B 创建客户端权威副本
  → A 用 throwerNetId + requestId 找到预测视觉球
  → A 将显示切换到权威副本，平滑处理位置差
  → B 直接显示权威副本
  → S 持续模拟刚体并发送运动快照
  → A、B 持续插值显示
```

拒绝后的下行：

```text
S 判断请求不满足规则
  → TargetRpc 把 requestId 和原因发送给 A
  → A 清理或淡出对应预测视觉球
  → A 更新道具界面与本地反馈
```

按键后立即得到的是视觉反馈。道具消耗、实体生成、命中和伤害在服务器接受与结算后成立。

## 4. 请求编号与网络编号各管什么

`requestId` 在投掷前由本地玩家分配。`netId` 在服务器建立网络实体时分配。

使用 `throwerNetId + requestId` 作为预测匹配键。A 的请求 7 与 B 的请求 7 分别属于各自玩家，预测服务按完整键保存记录。

每个记录保存：

```text
throwerNetId、requestId
预测视觉实例
本地创建时间
当前显示阶段
匹配到的权威 netId
结束或拒绝状态
```

请求编号在同一玩家网络生命周期内单调递增。玩家重新生成时按新的玩家身份建立记录。序号达到上限时停止分配，业务明确处理新的请求周期。

服务器保留已处理序号或有界的请求结果表，让同一请求只消耗一次道具、生成一次投掷物。基础链路使用可靠 Command，业务层按一次操作发送一次请求。增加主动重试时，重复请求返回缓存的同一结果。

## 5. 请求入口与服务器规则怎样编写

下面的类型放在共同参与客户端和服务器构建的代码中。请求结构中的公开字段交给 Mirror 序列化。

```csharp
using Mirror;
using UnityEngine;

public struct ThrowRequest
{
    public uint RequestId;
    public int ItemId;
    public Vector3 Direction;
    public float Charge;
}

public enum ThrowRejectReason : byte
{
    InvalidInput,
    ItemUnavailable,
    Cooldown,
    Blocked
}

public struct ProjectileLaunchState
{
    public uint ThrowerNetId;
    public uint RequestId;
    public int ItemId;
    public Vector3 Origin;
    public Vector3 InitialVelocity;
    public double LaunchTime;
    public double DetonateAt;
}

public struct ThrowPlan
{
    public NetworkProjectileState Prefab;
    public Vector3 Origin;
    public Vector3 InitialVelocity;
    public double FuseSeconds;
}
```

`ThrowPlan` 是服务器内部计划，包含 Prefab 引用。网络请求与同步状态传道具编号，服务器计划使用自己配置的 Prefab 引用。

规则服务与表现服务使用以下接口。接口是扩展练习的接入点，具体实现分别承接道具系统和本地视觉管理。

```csharp
public abstract class ThrowRules : MonoBehaviour
{
    public abstract bool TryApproveThrow(
        NetworkIdentity thrower,
        ThrowRequest request,
        out ThrowPlan plan,
        out ThrowRejectReason reason);
}

public abstract class LocalThrowPresentation : MonoBehaviour
{
    public abstract void BeginPrediction(ThrowRequest request, Transform playerRoot);
    public abstract void RejectPrediction(
        uint throwerNetId, uint requestId, ThrowRejectReason reason);
    public abstract void AttachAuthoritative(NetworkProjectileState projectile);
    public abstract void ForgetAuthoritative(NetworkProjectileState projectile);
}
```

`ThrowRules.TryApproveThrow` 只由服务器入口调用，按顺序完成：

1. 检查每连接请求速率与请求数值。
2. 查询服务器道具配置，检查玩家持有、冷却和使用状态。
3. 计算起点与初速度，检查出手空间、速度上限和引信范围。
4. 确认 Prefab 配置有效，形成 `ThrowPlan`。
5. 在同一次服务器调用中提交消耗与冷却，返回批准结果。

配置装载阶段验证所有道具 Prefab 和组件。消耗与生成采用同一业务事务；引入异步资源装载或可能失败的生成过程时，为事务定义提交和回滚。

`LocalThrowPresentation` 的实现放在玩家上的普通组件中，保存预测字典、创建视觉球、执行显示接管、清理记录。组件在本地玩家启动时启用输入相关表现，在玩家停止与场景退出时清理记录。

投掷入口如下：

```csharp
[RequireComponent(typeof(NetworkIdentity))]
public sealed class NetworkThrowAbility : NetworkBehaviour
{
    [SerializeField] private ThrowRules rules;
    private LocalThrowPresentation presentation;
    private uint nextRequestId;
    private uint lastProcessedRequestId;

    private void Awake()
    {
        presentation = GetComponent<LocalThrowPresentation>();
    }

    public void RequestThrow(int itemId, Vector3 direction, float charge)
    {
        if (!isLocalPlayer || !NetworkClient.ready
            || presentation == null || nextRequestId == uint.MaxValue)
        {
            return;
        }

        var request = new ThrowRequest
        {
            RequestId = ++nextRequestId,
            ItemId = itemId,
            Direction = direction,
            Charge = charge
        };

        presentation.BeginPrediction(request, transform);
        CommandThrow(request);
    }

    [Command]
    private void CommandThrow(ThrowRequest request)
    {
        if (request.RequestId <= lastProcessedRequestId)
        {
            return;
        }

        lastProcessedRequestId = request.RequestId;

        if (rules == null)
        {
            TargetRejectThrow(
                connectionToClient, request.RequestId,
                ThrowRejectReason.ItemUnavailable);
            return;
        }

        if (!rules.TryApproveThrow(
            netIdentity, request, out ThrowPlan plan,
            out ThrowRejectReason reason))
        {
            TargetRejectThrow(connectionToClient, request.RequestId, reason);
            return;
        }

        double now = NetworkTime.unscaledTime;
        var launch = new ProjectileLaunchState
        {
            ThrowerNetId = netId,
            RequestId = request.RequestId,
            ItemId = request.ItemId,
            Origin = plan.Origin,
            InitialVelocity = plan.InitialVelocity,
            LaunchTime = now,
            DetonateAt = now + plan.FuseSeconds
        };

        NetworkProjectileState projectile = Instantiate(
            plan.Prefab, plan.Origin, Quaternion.identity);
        projectile.ServerInitialize(launch);
        NetworkServer.Spawn(projectile.gameObject);
    }

    [TargetRpc]
    private void TargetRejectThrow(
        NetworkConnectionToClient target,
        uint requestId,
        ThrowRejectReason reason)
    {
        presentation?.RejectPrediction(netId, requestId, reason);
    }
}
```

`rules` 引用玩家 Prefab 中的服务器规则实现，或由服务器初始化时绑定规则服务。`presentation` 引用同一玩家根上的本地表现实现。输入层只调用 `RequestThrow`，界面与输入组件通过普通 C# 调用交接。

客户端执行 `RequestThrow` 中的本地代码。对 `CommandThrow` 的调用由 Mirror 生成发送包装，服务器收到消息后执行这里的 Command 方法体。`TryApproveThrow`、道具消耗、初始化和 Spawn 因此处于服务器链路。

这段入口按序处理单次可靠请求。重复序号直接结束服务器处理，预测记录等待原请求结果。需要业务重试时，把序号判定扩展为有界结果缓存。

## 6. 权威投掷物怎样初始化

网络投掷物根的 `NetworkRigidbodyReliable` 使用 `ServerToClient` 和 `Observers`。`Rigidbody` 与同步组件 Target 指向同一个网络根。

```csharp
[RequireComponent(typeof(NetworkIdentity), typeof(Rigidbody))]
public sealed class NetworkProjectileState : NetworkBehaviour
{
    [SyncVar] private ProjectileLaunchState launch;
    private Rigidbody body;

    public ProjectileLaunchState Launch => launch;
    public Rigidbody Body => body;

    private void Awake()
    {
        body = GetComponent<Rigidbody>();
    }

    [Server]
    public void ServerInitialize(ProjectileLaunchState value)
    {
        launch = value;
    }

    public override void OnStartServer()
    {
        base.OnStartServer();
        body.isKinematic = false;
        body.detectCollisions = true;
        body.useGravity = true;
        body.velocity = launch.InitialVelocity;
    }

    public override void OnStartClient()
    {
        base.OnStartClient();

        if (!isServer)
        {
            body.isKinematic = true;
            body.detectCollisions = false;
        }

        FindLocalPresentation()?.AttachAuthoritative(this);
    }

    public override void OnStopClient()
    {
        FindLocalPresentation()?.ForgetAuthoritative(this);
        base.OnStopClient();
    }

    private LocalThrowPresentation FindLocalPresentation()
    {
        NetworkIdentity player = NetworkClient.localPlayer;
        if (player == null || player.netId != launch.ThrowerNetId)
        {
            return null;
        }

        return player.GetComponent<LocalThrowPresentation>();
    }
}
```

先整体赋值发射结构，再调用 Spawn，让客户端初次接收就取得匹配键、起点、初速度和引信期限。后续修改结构状态时，也构造完整新值再赋给同步字段。

`OnStartServer` 设置一次发射初速度，之后由服务器物理推进。客户端刚体负责承载接收变换，玩法碰撞由服务器执行。相应的碰撞层仍按工程统一配置。

`NetworkServer.Spawn` 使用服务器控制归属。`ThrowerNetId` 用于归因与预测匹配，投掷物控制归属和投掷者身份分别表达。投掷者离开时，服务器按规则继续模拟或结束该投掷物。

这里只展示发射与接入表现的代码。下一章为同一权威对象补充阶段、引信与结算职责。

## 7. 接管时先保证一件东西在显示

本地表现服务收到 `AttachAuthoritative` 时按匹配键查询预测记录：

1. 匹配成功时，保留预测视觉球，暂时隐藏权威对象的模型子节点。
2. 权威对象初始状态已应用，显示根可用后开始接管。使用快照就绪或同步组件的应用时机观察这一条件。
3. 读取预测球当前世界位置，与权威显示根计算偏移。
4. 权威模型从这个视觉位置开始显示，销毁或淡出预测视觉球。
5. 逐帧缩小模型偏移，最终回到权威根。

初始 Spawn 变换可以作为等待上限后的显示依据。等待使用本地时间与有界超时。只隐藏模型，网络组件继续接收和应用状态。

匹配失败时，按权威状态直接显示。其他玩家的客户端沿这条路径运行。

### 用子节点消化位置差

以下是本地表现实现内部的接管计算。`authoritativeRoot` 指网络根，`visual` 指模型子节点。

```csharp
private Vector3 visualOffset;

private void BeginHandoff(
    Transform authoritativeRoot,
    Transform visual,
    Vector3 predictedWorldPosition)
{
    visualOffset = predictedWorldPosition - authoritativeRoot.position;
    visual.position = authoritativeRoot.position + visualOffset;
}

private void UpdateHandoff(
    Transform authoritativeRoot,
    Transform visual,
    float correctionRate)
{
    float rate = Mathf.Max(0f, correctionRate);
    visualOffset *= Mathf.Exp(-rate * Time.unscaledDeltaTime);
    visual.position = authoritativeRoot.position + visualOffset;
}
```

每个接管中的对象保存自己的偏移，`LateUpdate` 在网络根更新后应用视觉位置。模型默认本地位置为零时，上述计算直接适用；有出厂偏移的模型，先得到它在当前根变换下的标准世界位置，再围绕该位置计算修正。

指数衰减让不同渲染帧率得到接近的过渡速度。需要旋转过渡时，同样在模型子节点保存相对旋转并逐步靠近标准姿态。

过渡距离与时长设上限。服务器已经确认碰撞、视觉偏移穿过障碍或差距很大时，采用短淡出或直接显示权威位置。视觉过渡只改善显示，碰撞和伤害始终使用服务器根。

### 为什么同样初速度仍会产生差距

本地预测在按键时开始，服务器模拟在接受请求时开始，客户端权威副本又沿插值时间线显示。三者经过时间存在差距，弹跳与动态碰撞也会改变轨迹。

短暂视觉预测通过显示过渡结束这段差距。需要一直维持即时预测时，进一步保存带时间的运动历史、对齐权威采样时间并重放后续模拟，进入第 08 章说明的持续预测范围。

## 8. 拒绝、超时与提前爆炸怎么收尾

| 情况 | 本地处理 | 服务器含义 |
| --- | --- | --- |
| TargetRpc 拒绝 | 按完整键移除预测，更新反馈 | 请求结束，资源按拒绝规则处理 |
| 预测等待超时 | 清理或淡出视觉，记录已超时 | 服务器结果仍按正常链路成立 |
| 超时后 Spawn 到达 | 直接显示权威副本 | 已接受投掷继续存在 |
| 爆炸事件先到 | 清理对应预测，记录该键已结束 | 投掷物完成服务器结算 |
| 已结束对象的 Spawn 晚到 | 根据阶段和结束记录决定显示或隐藏 | 客户端按完整生命周期处理 |
| 玩家停止或场景退出 | 清理预测、过渡对象和结束记录 | 服务器按离开规则处理实体 |
| 权威对象停止 | 清理接管记录，尾迹与特效按自身时长结束 | 网络对象生命周期结束 |

结束记录采用有界缓存，按期限移除。清理按键查找，并允许重复调用，让拒绝、爆炸和销毁连续到达时得到同一结果。

接受确认可以用 TargetRpc 提前通知界面。预测接管以权威副本可用为条件，确认消息与 Spawn 分别表达各自的信息。

## 9. 按阶段落地与验证

1. 先完成请求、服务器校验、Spawn 和双客户端快照显示。
2. 加入请求编号与预测字典，检查每次投掷只生成一个权威实体。
3. 加入预测视觉与子节点过渡，测量接管等待和位置误差。
4. 接上拒绝、超时、停止与提前爆炸的清理。
5. 再按第 10 章加入弹跳、引信、伤害和击退。

验证记录用同一组编号串起上下行：

```text
玩家 netId / requestId
本地预测开始时间
服务器接受或拒绝结果
权威投掷物 netId / 发射时间
客户端收到实体与接管时间
结束原因与预测清理结果
```

双客户端分别验证自己投掷、对方投掷、快速连续投掷、库存耗尽、出手处有障碍、增加延迟、提前爆炸、断线和场景退出。观察权威实体数量、资源消耗次数、预测残留与接管误差。
