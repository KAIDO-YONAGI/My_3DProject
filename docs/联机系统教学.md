# 跟着本项目源码理解 Mirror 联机

这篇教程只讨论本项目的网络：进程怎样变成服务器、客户端怎样连上、网络玩家怎样生成、状态怎样传递，以及为什么 Dedicated Server 构建能够自动监听。文中链接指向当前工作区的配置和源码；`Assets/Mirror/` 是工程使用的 Mirror 插件本体。建议边读边打开链接，不需要先背 Mirror 的 API。

先建立一个贯穿全文的例子：一台机器运行专用服务器 S，玩家甲运行客户端 A，玩家乙运行客户端 B。服务器 S 创建两个 `Player_Network` 网络对象；A 和 B 各自收到这两个对象的副本。A 看自己的对象叫“本地玩家”，看乙的对象叫“远程玩家”；B 的视角正好相反。服务器没有“自己的本地玩家”。本文中的“本地”始终**相对于正在运行的那个客户端**，不是“与服务器在同一台电脑”。

几个容易混淆的名词：

| 名词 | 在本项目中指什么 |
| --- | --- |
| 服务器 / 客户端 | 运行 Mirror `NetworkServer` / `NetworkClient` 的进程；专用服务器只运行服务器一侧，Host 才在同一进程兼任两侧。 |
| `NetworkManager` | 管理启动、连接、玩家创建和注册 Prefab 的入口组件，位于 [NetworkManager.prefab](../Assets/Core/Prefabs/NetworkManager.prefab#L50)，运行时由 PersistentScene 带入。 |
| Transport / KCP | Mirror 以下的传输层，本项目使用 UDP 7777 上的 `KcpTransport`；它送消息，不决定角色长什么样。 |
| `NetworkIdentity` | 网络对象的身份组件。服务器和客户端靠 `netId` 对应同一个逻辑玩家，客户端仍然拥有各自的 Unity 对象副本。见 [Player_Network.prefab](../Assets/Core/Prefabs/Player_Network.prefab#L1)。 |
| owner / `isLocalPlayer` | 某客户端拥有哪个网络玩家；属于自己的玩家副本上 `isLocalPlayer` 为真，其他玩家副本上为假。不是“这份 Prefab 是否在本机”。 |
| `SyncVar` | `NetworkBehaviour` 中由服务器维护、同步到该对象的客户端观察者的字段；不是客户端写入即可广播。 |
| `[Command]` | 客户端在有权限的网络对象上发起请求，由服务器执行方法；不是本机直接修改服务器内存。 |
| 网络根对象 / 视觉模型 | `Player_Network` 是被 Mirror Spawn 的网络根；管理器后来 `Instantiate` 到它下面的角色 Prefab 是**每个客户端本地生成的视觉子对象**，不再单独 Spawn 一个网络玩家。 |

## 一、进程从哪里开始，为什么会分成服务器和客户端

### 1. 场景先让 NetworkManager 存在

[EditorBuildSettings.asset](../ProjectSettings/EditorBuildSettings.asset#L8) 当前启用了 `InitialScene`、`PersistentScene`、`MultiplayerSampleScene`。入口场景中的 [InitialLoad.Awake](../Assets/FrameWork/Scripts/Scene/InitialLoad.cs#L11) 开始加载 PersistentScene；后者以 Additive 方式进入运行时，于是场景里引用的 [NetworkManager 实例](../Assets/Core/Scenes/PersistentScene.unity#L796) 也进入运行时。加载场景**不等于**已经监听端口，它只是让组件的 `Start` / `Update` 有机会运行。另一个 [SceneChanger](../Assets/FrameWork/Scripts/Scene/SceneChanger.cs#L250) 负责加载玩法场景；本项目 [Mirror 的 `onlineScene` 留空](../Assets/Core/Prefabs/NetworkManager.prefab#L65)，所以这里不是 Mirror 的在线场景切换流程。

如果构建漏掉入口场景或 PersistentScene，即使有服务器目标平台、KCP 端口和玩家 Prefab，也可能根本没有活动的 `NetworkManager`。先追对象从哪里来，再追它怎样启动。

### 2. 同一份 NetworkManager Prefab 有两条启动入口

看 [NetworkManager.prefab](../Assets/Core/Prefabs/NetworkManager.prefab#L50) 上的实际字段：

| 配置 | 当前值 | 代码消费它的位置 |
| --- | --- | --- |
| `headlessStartMode` | `1`，对应 `AutoStartServer` | [Mirror 枚举及 NetworkManager.Start](../Assets/Mirror/Core/NetworkManager.cs#L10) 选择无图形服务器启动方式。 |
| `editorAutoStart` | `0` | [NetworkManager.Start](../Assets/Mirror/Core/NetworkManager.cs#L240) 在编辑器额外检查；普通 Play 不会仅凭 `headlessStartMode` 自启服务器。 |
| `transport` | `KcpTransport` | [SetupServer](../Assets/Mirror/Core/NetworkManager.cs#L301) 最后走 [NetworkServer.Listen](../Assets/Mirror/Core/NetworkServer.cs#L152)。 |
| KCP `Port` | `7777` | [KcpTransport.ServerStart](../Assets/Mirror/Transports/KCP/KcpTransport.cs#L192) 将端口交给 UDP Socket。 |
| `networkAddress` | `127.0.0.1` | [NetworkManager.StartClient](../Assets/Mirror/Core/NetworkManager.cs#L403) 的连接目标；客户端自动连接脚本会覆盖它。 |
| `playerPrefab` / `autoCreatePlayer` | `Player_Network` / `1` | [客户端连接回调](../Assets/Mirror/Core/NetworkManager.cs#L1390) 请求玩家，[服务端回调](../Assets/Mirror/Core/NetworkManager.cs#L1358) 实例化该 Prefab。 |
| `onlineScene` | 空 | [StartServer](../Assets/Mirror/Core/NetworkManager.cs#L333) 不等 Mirror 的在线场景加载完成后才 Spawn 场景物体。 |

第一条入口是 **Mirror 自己的服务器启动**：[Utils.IsHeadless](../Assets/Mirror/Core/Tools/Utils.cs#L46) 在 `UNITY_SERVER` 编译条件下返回真；[NetworkManager.Start](../Assets/Mirror/Core/NetworkManager.cs#L240) 在非编辑器的无图形运行环境读取 `headlessStartMode`，值为 `AutoStartServer` 就调用 `StartServer()`。普通有图形客户端不会因为这个设置启动服务器。`UNITY_SERVER` 是编译条件；`IsHeadless` 也有无图形设备的运行时判断，因此“专用服务器”与“使用普通构建但以无图形方式运行”的条件不要混为一谈。

第二条入口是项目自己的 [AutoStartClient.Update](../Assets/Core/Scripts/Networking/AutoStartClient.cs#L32)。同一 Prefab 上 [AutoStartClient 配置](../Assets/Core/Prefabs/NetworkManager.prefab#L140) 当前允许编辑器和普通 Player 自动连接，目标 `127.0.0.1`，重试间隔 3 秒。它先检查 `Application.isBatchMode`、`NetworkServer.active`、`NetworkClient.active`；任一为真就返回。接着按编辑器或构建 Player 的开关决定是否尝试，等 `NetworkManager.singleton` 出现后把 `manager.networkAddress` 改为 `connectAddress`，再调用 `manager.StartClient()`。

这里每个 Mirror 属性都在回答不同问题：`NetworkServer.active` 是“本进程是否已启动服务器”，用来阻止服务器再作为普通客户端自动连接；`NetworkClient.active` 是“本进程的客户端是否已启动（包括仍在连接中）”，用来阻止重复发起连接；`NetworkManager.singleton` 是场景中有效的管理器实例，没有它就没有可调用的 `StartClient`；`networkAddress` 是即将传给 `NetworkClient.Connect` 的目标地址，不是服务器监听地址。`StartClient()` 只把管理器切到客户端模式、注册客户端消息和 Prefab、发起传输连接，**此刻尚未拥有玩家，也不意味着连接已成功**。

这里的 3 秒是**两次尝试的最小间隔**，不是首次启动先等 3 秒：`nextConnectAttempt` 初始为零，条件满足时首次尝试可以立即开始。`NetworkClient.active` 包括连接中的状态，因此每帧 Update 不会重复 `StartClient`；失败或断线回到非活动状态后，才可能按间隔重试。[源码的计时和判断](../Assets/Core/Scripts/Networking/AutoStartClient.cs#L35) 比“会自动重连”四个字更能说明具体行为。

于是服务器构建里的入口链是：

```text
InitialScene -> InitialLoad -> PersistentScene 中的 NetworkManager
  -> Mirror NetworkManager.Start 检测 headlessStartMode
  -> StartServer -> 监听 UDP 7777
```

普通图形客户端的入口链是：

```text
InitialScene -> InitialLoad -> PersistentScene 中的 NetworkManager + AutoStartClient
  -> AutoStartClient.Update 检查进程状态、开关和重试时间
  -> networkAddress = connectAddress -> StartClient -> 连接服务器
```

注意专用服务器不应该自己跑成普通客户端：batch mode 检查会阻止 `AutoStartClient`，而 `NetworkServer.active` 在服务器已启动后也能阻止它。这与 Mirror 的 `headlessStartMode` 分工不同，一个负责**何时开服**，一个负责**何时自动连接**。

这也回答“服务器逻辑到底在哪”：项目自己的 [AutoStartClient.cs](../Assets/Core/Scripts/Networking/AutoStartClient.cs#L7) 决定普通客户端何时接入，[NetworkCharacterSync.cs](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L8) 决定角色编号的服务器写入和客户端请求；通用服务器生命周期和玩家生成则在插件的 [Mirror NetworkManager.cs](../Assets/Mirror/Core/NetworkManager.cs#L333)、[NetworkServer.cs](../Assets/Mirror/Core/NetworkServer.cs#L152)。寻找服务器逻辑时不要只在 `Assets/Core/Scripts/Networking/` 中搜索：项目通过 Prefab 配置调用了 `Assets/Mirror/` 的实现。

还有一个时间上的要求：`InitialLoad` 必须让 PersistentScene 中的角色管理器在网络玩家 `OnStartServer` / `OnStartClient` 需要它时已经存在。当前 [NetworkCharacterManager.Awake](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L54) 设置 `Instance`；如果运行时没加载这场景，[NetworkCharacterSync.OnStartServer](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L28) 虽会退回编号 0，客户端 [ApplyCharacter](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L114) 却因找不到管理器不能装模型。**默认编号有回退值，不代表可以省略 PersistentScene。**

## 二、从 UDP 到 Mirror 连接，再到一个玩家

### 1. 服务器在哪里真正监听

沿着方法往下点：

```text
NetworkManager.StartServer
  -> SetupServer
  -> NetworkServer.Listen(maxConnections)
  -> Transport.active.ServerStart()
  -> KcpTransport.ServerStart()
  -> KcpServer.Start()
  -> 创建并绑定 UDP Socket :7777
```

[StartServer](../Assets/Mirror/Core/NetworkManager.cs#L333) 先拒绝重复启动，把管理器模式设为 `ServerOnly`，再调用 [SetupServer](../Assets/Mirror/Core/NetworkManager.cs#L301)。`SetupServer` 初始化单例、应用服务器设置、调用 [NetworkServer.Listen(maxConnections)](../Assets/Mirror/Core/NetworkServer.cs#L152)，然后注册管理器处理的服务器消息。`Listen` 先检查 Mirror 的代码生成结果和活动 Transport，接入 Transport 的事件处理，把连接上限交给服务器，调用 `Transport.active.ServerStart()`，最后标记 `NetworkServer.active` 并注册默认消息处理器；`maxConnections` 只限制连接数，不会自己打开端口。本工程活动 Transport 是 [KcpTransport](../Assets/Mirror/Transports/KCP/KcpTransport.cs#L192)：它的 `ServerStart()` 把配置的 `Port` 交给 [KcpServer.Start](../Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpServer.cs#L149)。后者创建非阻塞 UDP Socket 并绑定 7777，[Socket 配置](../Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpServer.cs#L70) 决定 IPv4/IPv6 等细节。**绑定成功才有可接收数据报的端口**；`NetworkServer.active` 是 Mirror 的运行状态，不能把它与外部网络确实可达画等号。

服务器仍然运行 Unity 的场景和脚本，只是以服务器模式运行 Mirror；项目没有另一套单独编写的网络服务程序。服务器并非“保存客户端发来的所有对象”，而是负责连接、身份、玩家生成和同步消息的权威一侧。

`SetupServer` 的先后顺序值得看一遍：[RegisterServerMessages](../Assets/Mirror/Core/NetworkManager.cs#L746) 在 `Listen` 注册默认处理器之后，接管连接、`AddPlayerMessage` 和 `ReadyMessage` 等入口：这样客户端发来的“添加玩家”“已经准备好”才会落到管理器相应回调，而不只是成为一包 UDP 数据。[StartServer](../Assets/Mirror/Core/NetworkManager.cs#L333) 随后调用管理器的 `OnStartServer`，给游戏代码一个“服务器已活动，可以生成网络对象”的时机；本项目没有在这里手写玩家创建。最后因当前 `onlineScene` 为空，`NetworkServer.SpawnObjects()` 扫描并生成**场景中已有的 NetworkIdentity 对象**，不是创建每个连接的 `Player_Network`；后者要等 AddPlayer。这里 `NetworkManager.OnStartServer` 是**管理器生命周期**，后面新玩家的 `NetworkCharacterSync.OnStartServer` 是**玩家组件生命周期**，名称相同但对象和时机都不同。

传输事件需要 Unity 帧循环驱动。Mirror 注册的 [NetworkServer 传输回调](../Assets/Mirror/Core/NetworkServer.cs#L228) 把底层“有人连入 / 有消息 / 已断开”转换为 Mirror 的连接和消息处理；[KcpTransport 的 EarlyUpdate/LateUpdate](../Assets/Mirror/Transports/KCP/KcpTransport.cs#L179) 分别推进接收与待发送数据。监听 Socket 创建后程序不能立刻退出；构建出的服务器仍须持续运行，才会处理新连接、Command 和同步状态。这也是为什么“控制台显示启动成功”不足以证明后面整条链正常。

### 2. 客户端发起连接，KCP 和 Mirror 各做什么

[AutoStartClient](../Assets/Core/Scripts/Networking/AutoStartClient.cs#L70) 调用 `StartClient` 后，[Mirror NetworkManager.StartClient](../Assets/Mirror/Core/NetworkManager.cs#L403) 先检查地址和重复启动，设置 `ClientOnly`、注册客户端消息处理，并用 `NetworkClient.RegisterPrefab(playerPrefab)` 登记“收到这个 Prefab 的 Spawn 标识时该造哪种本地对象”。然后 [NetworkClient.Connect(networkAddress)](../Assets/Mirror/Core/NetworkClient.cs#L207) 把状态设为 `Connecting`，向活动 Transport 发起连接；此调用返回不代表已经连上。[KcpTransport.ClientConnect](../Assets/Mirror/Transports/KCP/KcpTransport.cs#L158) 把地址和自身的 `Port` 传下去；[KcpClient.Connect](../Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpClient.cs#L91) 解析地址、创建非阻塞 UDP Socket 并发送 Hello，[KcpPeer](../Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpPeer.cs#L331) 处理握手状态和 Cookie。传输层确认连接后，[NetworkClient.OnTransportConnected](../Assets/Mirror/Core/NetworkClient.cs#L268) 才把状态改成 `Connected` 并触发管理器注册的连接事件；**连接成功仍不等于 Ready 或已有玩家**。

这里有**三个层次**，别把它们叫作同一个“同步”：

1. UDP 负责把数据报送到指定 IP 和端口；它自己不提供可靠送达、顺序或玩家概念。
2. 项目选择的 [KCP 传输](../Assets/Mirror/Transports/KCP/KcpTransport.cs#L99) 在 UDP 上组织握手、可靠/不可靠通道和收发。其 [EarlyUpdate/LateUpdate](../Assets/Mirror/Transports/KCP/KcpTransport.cs#L179) 驱动收包和发包；[KcpPeer.SendData](../Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpPeer.cs#L711) 按通道送数据。用了 UDP 不等于每条 Mirror 消息都是“不可靠地随便发”。
3. Mirror 在连接之上处理 Ready、玩家生成、网络身份和各 `NetworkBehaviour` 的状态。KCP 不认识 `Player_Network`，也不替你选择角色 Prefab。

KCP 的 Hello/Cookie 握手是传输层的连接过程，不等于项目做了账号登录或业务认证。当前 [NetworkManager.prefab](../Assets/Core/Prefabs/NetworkManager.prefab#L50) 的 `authenticator` 为空；Mirror 的 [连接认证处理](../Assets/Mirror/Core/NetworkManager.cs#L1148) 在没有 Authenticator 的情况下直接将连接标为可用。不要因为日志显示“connected”就推断存在用户身份认证。

如果想把连接事件再跟深一层：[RegisterClientMessages](../Assets/Mirror/Core/NetworkManager.cs#L757) 把 `OnClientConnectInternal` 挂到 `NetworkClient.OnConnectedEvent`，还注册 Spawn 等消息所需的玩家 Prefab。[OnClientConnectInternal](../Assets/Mirror/Core/NetworkManager.cs#L1211) 本可把连接交给 Authenticator；当前 `authenticator` 为空，就直接调用 [OnClientAuthenticated](../Assets/Mirror/Core/NetworkManager.cs#L1228)。这个方法把当前连接标为 `isAuthenticated`，并因 `onlineScene` 为空将 `clientLoadedScene` 设为假，接着调用默认 `OnClientConnect`。这里的“认证通过”只是 Mirror 无认证器时放行，**不是**账号验证；`clientLoadedScene=false` 则使下面的 Ready/AddPlayer 不必等 Mirror 的在线场景切换。

`connectAddress` 是客户端要去的机器，`127.0.0.1` 永远指客户端自己的机器。A 与 S 在不同电脑时，默认地址会让 A 去连接 A 自己；还需要服务器的 UDP 7777 对 A 可达。`networkAddress` 虽然也在 Prefab 上，但 [AutoStartClient](../Assets/Core/Scripts/Networking/AutoStartClient.cs#L70) 发起自动连接前会用 `connectAddress` 覆盖它，所以排查“地址怎么变了”应先看这个脚本。

### 3. 连上并不等于已经有玩家：Ready、AddPlayer、Spawn

传输连接建立后，Mirror 的 [NetworkManager.OnClientConnect](../Assets/Mirror/Core/NetworkManager.cs#L1390) 才处理玩家创建。本项目 `onlineScene` 为空且 `autoCreatePlayer` 为真，所以默认回调继续做两件事：

```text
客户端 OnClientConnect
  -> NetworkClient.Ready()       表示准备接收网络对象
  -> NetworkClient.AddPlayer()   发送“给我的连接创建玩家”的请求
```

[NetworkClient.Ready()](../Assets/Mirror/Core/NetworkClient.cs#L1063) 要求连接已存在且尚未 Ready；它先把客户端和连接标为 Ready，再发送 `ReadyMessage`。服务器收到后用 `NetworkServer.SetClientReady(conn)` 标记对应连接，使它有资格接收现有网络对象和后续状态。Ready 的对象是**连接**，并未创建玩家。[NetworkClient.AddPlayer()](../Assets/Mirror/Core/NetworkClient.cs#L1114) 则要求连接存在、已经 Ready、尚无自己的 `connection.identity`；它发送 `AddPlayerMessage`，表示“请服务器为这条连接创建玩家”。两个调用都不是在客户端 `Instantiate` 权威玩家，也没有让客户端自己决定出生位置。若 `onlineScene` 改为非空，Mirror 会在场景加载相关时机再走这一步；本文只描述**当前空配置**。

为什么两条消息要分开？Ready 描述的是“这个连接可以进入网络世界”，不是“角色模型已经完成”；服务器标记 Ready 后是否立刻发所有既有对象，还取决于玩家身份建立和观察关系。[OnServerAddPlayerInternal](../Assets/Mirror/Core/NetworkManager.cs#L1192) 是服务器给 `AddPlayerMessage` 注册的处理器，先检查 `playerPrefab` 是否存在且带 `NetworkIdentity`，通过才转给 `OnServerAddPlayer`。这里先挡掉无效 Prefab，不会因为收到消息就自动拥有一个玩家；只看到“Connected”时不能跳过这些状态排查。

服务器在 [OnServerAddPlayer](../Assets/Mirror/Core/NetworkManager.cs#L1358) 调用 `GetStartPosition()`，用返回的 Transform 位置/旋转实例化 `playerPrefab`；如果没有起点就按 Prefab 默认位置创建。PersistentScene 里配置了 [NetworkStartPosition](../Assets/Core/Scenes/PersistentScene.unity#L500)，`playerSpawnMethod: 0` 使 [GetStartPosition](../Assets/Mirror/Core/NetworkManager.cs#L1128) 从已注册起点随机选一个。注意普通 `Instantiate` 此时**只在服务器上造出 GameObject**，它尚未因这行代码而出现在 A/B 客户端；后面的 `AddPlayerForConnection` 才使它成为该连接的网络玩家。位置选择不是 `NetworkCharacterManager` 在决定网络出生点。

进一步看 [NetworkServer.AddPlayerForConnection(conn, player)](../Assets/Mirror/Core/NetworkServer.cs#L1241)：`conn` 是发请求的服务器侧连接，`player` 是刚创建的服务器侧对象。没有 `NetworkIdentity` 或连接已有玩家就返回失败；通过后 `conn.identity = identity` 建立“这条连接的玩家是谁”，`identity.SetClientOwner(conn)` 记录“谁有权限操作此网络对象”。接着 `SetClientReady` 确保连接已准备好接收网络对象，`Respawn(identity)` 在首次生成时转到 `Spawn`。这使服务器能验证后续来自甲的 Command，而不只是听客户端自称“我是甲”。Host 模式还为本地连接直接设拥有者并登记本地玩家，不走远端客户端收包的完整路径。

首次 [NetworkServer.Spawn](../Assets/Mirror/Core/NetworkServer.cs#L1704) 为 `NetworkIdentity` 分配 `netId`（这次联机会话里对应对象的网络编号），放进服务器的已生成对象表，再调用各 `NetworkBehaviour.OnStartServer`；本项目的 `NetworkCharacterSync` **在这里读取默认角色编号并写入 SyncVar**。随后 Mirror 建立观察者关系，[NetworkServer.SendSpawnMessage](../Assets/Mirror/Core/NetworkServer.cs#L1535) 才针对每个可见该对象的连接构造 Spawn：带 `netId`、场景/Prefab 标识、Transform、身份标记及各组件的**初始**序列化数据。客户端事先由 [NetworkManager.RegisterClientMessages](../Assets/Mirror/Core/NetworkManager.cs#L757) 调用 `NetworkClient.RegisterPrefab(playerPrefab)`，才能按 Prefab 标识创建相应副本；传输的不是 Unity Prefab 文件。`SpawnObjects()` 扫场景预置对象，`Spawn()` 处理这个动态玩家，`SendSpawnMessage()` 则是给具体连接发“如何在客户端表示这个对象”的消息，三者不能互换。

在 `SendSpawnMessage` 中，同一个玩家对象面向不同连接的消息并不完全相同：[服务器按 `identity.connectionToClient == conn` 计算 `isOwner`](../Assets/Mirror/Core/NetworkServer.cs#L1535)，意思是“该连接拥有此对象”；按 `conn.identity == identity` 设置 `isLocalPlayer`，意思是“此对象就是该连接自己的玩家”。甲的 Spawn 到 A 时两者为真；到 B 时为假。Mirror 还按拥有者与观察者选取相应的初始状态负载。因此这两个布尔值是服务器针对**接收该消息的连接**确定的，不能当成 Prefab 里固定的标记。

客户端收到 Spawn 后，先按 Prefab 标识找到/创建对象，再在 [NetworkClient.ApplySpawnPayload](../Assets/Mirror/Core/NetworkClient.cs#L1143) 把它登记进本地 `spawned[netId]`，设置 `isOwner`、`isLocalPlayer` 等身份，最后用 `DeserializeClient(initialState: true)` 把消息中的各组件初始字段写入对象。**先设身份再反序列化**，是为了 SyncVar hook 此时也能知道该用本地还是远程模型。随后 [InvokeIdentityCallbacks](../Assets/Mirror/Core/NetworkClient.cs#L1479) 调用 `NetworkIdentity.OnStartClient`，由它通知同根上的组件；只有自己的玩家还调用 `OnStartLocalPlayer`。首批对象可能等批量 Spawn 完成才统一触发这些回调，不能假定收到一个包就立即完成所有装配。可以用 A/B 的例子检验：

| 副本所在进程 | S 创建的甲玩家 | S 创建的乙玩家 |
| --- | --- | --- |
| 客户端 A | A 的本地玩家，`isLocalPlayer = true` | A 看见的远程玩家，`false` |
| 客户端 B | B 看见的远程玩家，`false` | B 的本地玩家，`true` |
| 专用服务器 S | 两个服务器侧网络对象；不是客户端本地玩家 | 同左 |

所以“服务器生成两个人”不等于“每台客户端只存在自己的玩家”，也不等于“每台客户端从网络下载两套 Prefab”。每台客户端用**已随构建打包的** `Player_Network` 资源生成自己的对象副本，然后应用服务器同步来的状态。

初次进入一个已有玩家的房间时，“新连接收到已存在对象”与“服务器又生成了一个新玩家”也要区分。前者是既有服务器对象向新连接发送 Spawn，客户端据 `netId` 建立副本；后者来自新连接的 AddPlayer 请求，服务器会多创建一个玩家。`NetworkIdentity` 将 `OnStartServer`、`OnStartClient`、`OnStartLocalPlayer` 等回调转发给同一网络根上的各 [NetworkBehaviour](../Assets/Mirror/Core/NetworkIdentity.cs#L735)，所以本项目继承 `NetworkBehaviour` 的 `NetworkCharacterSync` 才会收到它们；普通视觉子对象不因父对象被 Spawn 就自动得到独立的网络身份。

## 三、角色编号：从服务端字段变成每台客户端的模型

先看三个东西放在哪里。[Player_Network.prefab](../Assets/Core/Prefabs/Player_Network.prefab#L1) 是有 `NetworkIdentity` 的网络玩家根；[NetworkCharacterSync.cs](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L8) 挂在根上，保存同步编号；[NetworkCharacterManager.cs](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L9) 在 PersistentScene 中，持有两套视觉 Prefab 数组和默认编号。**编号同步**和**模型装配**不是同一次操作。

### 1. 为什么 DefaultCharacterId 那条注释有四步

[PersistentScene.unity](../Assets/Core/Scenes/PersistentScene.unity#L299) 给管理器配置 `localCharacterPrefabs`（本地表现）、`characterPrefabs`（远程表现）以及 [当前 `defaultCharacterId: 0`](../Assets/Core/Scenes/PersistentScene.unity#L338)。角色编号就是数组下标：0 对应两套数组的第 0 项，1 对应第 1 项。C# 的 [DefaultCharacterId 属性](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L52) 只是返回字段：

```csharp
public int DefaultCharacterId => defaultCharacterId;
```

它没有验证数组、没有发网络消息、没有实例化对象。服务端新玩家的 [NetworkCharacterSync.OnStartServer](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L28) 才实际读取它，并写入字段：

```csharp
characterId = NetworkCharacterManager.Instance != null
    ? Mathf.Max(0, NetworkCharacterManager.Instance.DefaultCharacterId)
    : 0;
```

这里的 `Mathf.Max(0, ...)` 只防负数；管理器不存在时退回 0。**它并没有检查“数组第 0 项真的有 Prefab”**。假如默认编号在场景配置中越界，服务器照样能写编号，客户端到了装配阶段才会因缺 Prefab 发出警告。

该字段标记为 [SyncVar](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L12)：

```csharp
[SyncVar(hook = nameof(OnCharacterIdChanged))]
private int characterId;
```

对这个字段而言，“服务器维护”指玩家组件的 `OnStartServer`（每个服务器侧网络玩家首次 Spawn 时运行）或服务器处理改角色请求时写值；它不同于前面的 `NetworkManager.OnStartServer`。`[SyncVar]` 使字段参加该 `NetworkBehaviour` 的网络序列化：首次 Spawn 带完整初始值，已存在对象的后续变化进入状态更新，发送给观察该对象的客户端。每台客户端的 `NetworkCharacterSync` 都是自己的副本，Mirror 用 `netId` 和组件位置把收到的值写到正确对象，不是共享服务器内存。`hook = nameof(OnCharacterIdChanged)` 指明**本地字段在同步应用时**要调用的方法；它接收旧值、新值，但不会把方法本身发到网络上。项目的 [OnCharacterIdChanged](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L108) 忽略参数，调用 `ApplyCharacter()` 读取已经更新的字段；初始反序列化也可能触发 hook。

写 `characterId = 1` 看似普通赋值，Mirror 为什么知道要同步？这个类继承 `NetworkBehaviour`，编译时 Mirror 的 Weaver 会为 `[SyncVar]` 字段生成读写逻辑；[GeneratedSyncVarSetter](../Assets/Mirror/Core/NetworkBehaviour.cs#L567) 比较新旧值，变化时记录 dirty bit（“本组件哪个同步字段变脏”的标记）。Mirror 按发送节奏让 [NetworkIdentity.SerializeServer_Broadcast](../Assets/Mirror/Core/NetworkIdentity.cs#L1160) 序列化需要更新的组件与字段，再向观察者发送 Entity State；客户端收到后按 `netId` 找对象、反序列化字段并可能触发 hook。**普通客户端直接对自己的副本赋值不等于改动服务器字段**，也不自动让其他人看到它。Host 的服务器/本地客户端共享对象，setter 可直接触发本地 hook，这是后文 Host 特例的一部分。`SyncVar` 也不是每帧把整个 GameObject 复制到网络上。

**初始生成与后续改值要分开理解。** 远端客户端在 [ApplySpawnPayload](../Assets/Mirror/Core/NetworkClient.cs#L1143) 反序列化 Spawn 初始值；[NetworkCharacterSync.OnStartClient](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L41) 主动调用 `ApplyCharacter()`，即使之后没有任何编号变化，也能按当前编号装模型。自己的玩家还进入 [OnStartLocalPlayer](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L50)，确认本地身份后再应用一次，以选择本地数组；管理器缓存同编号的实例，所以不必再造一个。Host 不需要通过远端 Spawn 包取得服务器字段。以后服务器修改 SyncVar 时，收到变化的客户端由 hook 进入相同的装配入口。

一个值得注意的时序细节是 [ApplySpawnPayload](../Assets/Mirror/Core/NetworkClient.cs#L1143) 先设好 `netId`、拥有者和本地玩家标记，再 `DeserializeClient`；该反序列化**也可能触发 SyncVar hook**，并非“初始值绝对不触发 hook”。随后才有 `OnStartClient` / `OnStartLocalPlayer`，初次批量 Spawn 的回调甚至可能推迟到批量完成。三个入口都把**同一个网络玩家和编号**交给 [NetworkCharacterManager.ApplyCharacter](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L155)：它按 `isLocalPlayer` 选择数组，按编号检查 Prefab，已有同编号实例则复用，否则移除旧实例并在网络根下实例化新的视觉子物体。这解释了为什么多次 Apply 不必产生多个模型；这里没有再次调用 `NetworkServer.Spawn`。

调用链可以照着源码依次点开：

```text
PersistentScene.defaultCharacterId
  -> NetworkCharacterManager.DefaultCharacterId     只返回配置
  -> NetworkCharacterSync.OnStartServer              服务器写 characterId
  -> Mirror Spawn 初始状态 / 后续 SyncVar 状态       传给观察者
  -> OnStartClient / OnCharacterIdChanged             客户端应用编号
  -> NetworkCharacterSync.ApplyCharacter             转交管理器
  -> NetworkCharacterManager.ApplyCharacter          客户端本地装模型
```

### 2. “本地模型”和“远程模型”究竟怎么选

[NetworkCharacterManager.ApplyCharacter](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L155) 看的是传入玩家的 `IsLocalPlayerCharacter`，其来源就是 Mirror 的 `isLocalPlayer`：

```text
if 是当前客户端自己的玩家：
    从 localCharacterPrefabs[characterId] 找本地模型
else：
    从 characterPrefabs[characterId] 找远程模型
```

源码分别通过 [TryGetLocalCharacterPrefab](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L134) 和 [TryGetCharacterPrefab](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L121) 查找；缺配置时警告并返回。拿到 Prefab 后通过 [Instantiate(prefab, player.transform)](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L183) 作为网络根的子对象创建，记录实例和编号，以便相同编号复用、切换角色时替换，离开时由 [RemoveCharacter](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L226) 清理。这些视觉子对象的 Prefab **不靠 SyncVar 跨网络发送**；发送的是整数，客户端凭自己的 PersistentScene 配置找资源。

举例：S 给甲、乙的 `characterId` 都写 0。A 上甲的副本选本地数组 0、乙的副本选远程数组 0；B 上甲选远程数组 0、乙选本地数组 0。即使四个视觉实例长得相似，它们是四个本地实例，不是服务器把同一个 Unity 对象搬到两台机器。两套数组同下标必须对应同一角色，且客户端构建需包含相应资源，否则编号正确也无法显示。

`NetworkCharacterManager` 还做表现层组件的整理；那是“模型装上后在本地如何显示”的工作，本篇不展开相机、动画或物理。要抓住网络边界：**网络根由 Mirror 创建并有 `NetworkIdentity`；视觉子对象由项目管理器按收到的编号在本地创建。**

### 3. 客户端想换角色，为什么不能直接改 SyncVar

假设 A 想换成编号 1，调用入口是自己的玩家对象上的 [SetLocalCharacter(1)](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L70)。它先要求 `isLocalPlayer` 为真，且当前客户端的管理器能通过 [IsValidCharacterId](../Assets/Core/Scripts/Networking/NetworkCharacterManager.cs#L108) 检查：编号非负、没有超出任一数组，并且两侧 Prefab 都非空。普通客户端随后调用标记为 `[Command]` 的 [CmdSetCharacter(1)](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L94)。

`[Command]` 的调用看起来像普通方法，网络意义却不同：Weaver 把普通客户端调用 `CmdSetCharacter(1)` 变成发给服务器的 Command 消息，包含目标网络对象/组件/方法和参数；服务器找到对应的网络对象后才在**服务器进程**执行方法体。此 Command 使用 Mirror 默认的拥有者权限，A 不能用乙的玩家对象随便改乙的编号；服务器还要**再次**用自己的 `NetworkCharacterManager.IsValidCharacterId` 检查编号，成功才写 `characterId = requestedCharacterId`。客户端预检只为避免无意义请求，不能代替服务器校验。Command 也没有“返回新模型给 A”：字段变更后仍走 SyncVar 状态发送，A/B 各自在本地选模型。

接下来并非 Command 直接把模型传给 B，而是：

```text
A：SetLocalCharacter(1)
  -> [Command] CmdSetCharacter(1) 在 S 上执行
S：验证并写自己的 characterId = 1
  -> Mirror 同步这个 SyncVar 的新值
A：收到值 1 -> hook -> 从本地数组取 1，更新甲模型
B：收到值 1 -> hook -> 从远程数组取 1，更新甲模型
```

Host 的本地玩家和服务器同处一个进程，因此 [SetLocalCharacter 的 `NetworkServer.active` 分支](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L79) 直接写服务器字段，并立即调用本地 `ApplyCharacter()`。此时 Host 的本地 hook 也可能因服务器 setter 触发，重复装配会复用已有实例；其他远端客户端仍通过状态更新收到新编号。这个特例**不能**推广成“所有客户端直接改 SyncVar 都可以”；专用服务器加普通客户端时仍要走 Command。[NetworkCharacterSync.OnStopClient](../Assets/Core/Scripts/Networking/NetworkCharacterSync.cs#L60) 是客户端网络对象停止时的回调，会让管理器移除它的视觉实例与缓存，不是向服务器发“删除角色”的请求。

### 4. 位姿同步是另一套组件，不是 characterId 的附赠功能

[Player_Network.prefab](../Assets/Core/Prefabs/Player_Network.prefab#L69) 上还有 `NetworkTransformReliable`，其 `syncDirection: 1` 为 `ClientToServer`，配置同步位置和旋转、不传缩放；[NetworkCharacterSync 组件](../Assets/Core/Prefabs/Player_Network.prefab#L173) 则按服务器到客户端的方向同步角色编号。两个组件都在同一网络根上，但**各管各的数据**。

`NetworkTransformReliable.OnSerialize(writer, initialState)` 将这个组件的位姿写入网络负载：首次状态写所选位置/旋转的完整值，后续按该组件的压缩与快照规则写更新；它**不负责**角色编号。[OnClientToServerSync](../Assets/Mirror/Components/NetworkTransform/NetworkTransformReliable.cs#L348) 在服务器反序列化拥有者发来的位姿后，先确认 `syncDirection == ClientToServer`，检查服务器快照缓冲限制，再把快照放入服务器缓冲；不是在这里直接把玩家“传送”到服务器当前位置。服务器随后将可观察到的位姿状态送给其他客户端；其他客户端的 [OnServerToClientSync](../Assets/Mirror/Components/NetworkTransform/NetworkTransformReliable.cs#L379) 不对有权限的本地玩家重复应用服务器副本，而是把远程快照放入客户端缓冲，供后续插值显示。于是 B 看到甲移动走“A -> S -> B”，不是 A 直接给 B 发 Transform。该设置只说明位姿的同步方向，**不等于服务器已经实现权威移动校验、预测或回滚**；角色编号的“Command 请求 -> 服务器决定 -> SyncVar 发结果”也不能误套到位姿组件上。

## 四、Dedicated Server 构建为什么能运行这条链

构建不是“点击 Server 就自动拥有联机功能”。本项目能工作，是下面几个条件在**同一构建和运行过程**中接上了：

1. **资源被打包。** [Build Settings 启用的场景](../ProjectSettings/EditorBuildSettings.asset#L8) 包括入口及 PersistentScene；后者引用 NetworkManager，NetworkManager 又指向 [Player_Network Prefab](../Assets/Core/Prefabs/NetworkManager.prefab#L67) 和 KCP Transport。构建输出的文件名或目录不决定网络模式，但漏掉场景或引用会让之后的代码没有对象可运行。
2. **服务器模式被选中。** Windows Dedicated Server 构建带 `UNITY_SERVER` 条件，[Mirror Utils.IsHeadless](../Assets/Mirror/Core/Tools/Utils.cs#L46) 在此条件下为真。[NetworkManager.Start](../Assets/Mirror/Core/NetworkManager.cs#L240) 对**非编辑器**无图形环境读取 `headlessStartMode: AutoStartServer`，调用 `StartServer`。因此“构建目标”并非直接绑定 UDP 端口，它使启动判断的条件成立。[`editorAutoStart: 0`](../Assets/Core/Prefabs/NetworkManager.prefab#L52) 解释了普通编辑器 Play 为什么不自动开服；要在编辑器开服需要明确采取另一种启动方式，而不是误以为这个字段无效。
3. **服务器真的开始监听。** [StartServer -> SetupServer](../Assets/Mirror/Core/NetworkManager.cs#L333) 建立 ServerOnly 的 Mirror 状态，[Listen](../Assets/Mirror/Core/NetworkServer.cs#L152) 调用 [KcpTransport.ServerStart](../Assets/Mirror/Transports/KCP/KcpTransport.cs#L192)，[KcpServer](../Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpServer.cs#L149) 才绑定 UDP 7777。若端口被占用、对象没加载或在 `StartServer` 之前失败，程序能启动也不代表服务器在监听。
4. **普通客户端走另一分支。** 图形客户端没有上述自动开服条件，但 [AutoStartClient.Update](../Assets/Core/Scripts/Networking/AutoStartClient.cs#L32) 在开关允许且无活动 Server/Client 时调用 `StartClient`。它使用 `connectAddress` 指定服务器；A、B 客户端各自发起连接，再走 Ready / AddPlayer / Spawn。
5. **双方有同一套网络约定。** 服务端 `playerPrefab` 能 Spawn，客户端有注册的 Prefab 能识别 Spawn，`NetworkCharacterSync` 同步的是编号而非资源，两边的角色数组含义须对应。构建一个空壳服务器程序，或者只复制 `.exe` 而缺其构建数据，都不能靠网络在运行时补齐 Unity 资源。

一次完整时序可以拿来对照日志与层级面板：

```text
S 启动 -> PersistentScene -> NetworkManager.Start -> StartServer -> UDP :7777
A 启动 -> PersistentScene -> AutoStartClient -> StartClient -> KCP 连接 S
A 的 OnClientConnect -> Ready -> AddPlayer 请求
S 的 OnServerAddPlayer -> 创建甲的 Player_Network -> OnStartServer 写默认 characterId
S 的 Spawn -> A 获得甲副本 -> OnStartClient / OnStartLocalPlayer -> 本地模型
B 连接 -> S 创建乙 -> S 向 A、B 发相应 Spawn
A 看乙为远程模型；B 看甲为远程模型、看乙为本地模型
A 发起换角色 Command -> S 更新 SyncVar -> A、B 各自重装甲的视觉模型
```

操作只需抓住必要条件：Unity 分别构建 Windows Dedicated Server 和普通 Windows 客户端，保持入口/PersistentScene 等场景启用；先启动服务器，再启动客户端。工程约定的构建产物位置是 `D:/Unity/Releases/3D_MultiplayerGame/`，这个路径只是存放位置，**不参与**启动分支的条件判断。当前源码中没有负责这一流程的自定义 `BuildPipeline.BuildPlayer` 脚本；实际使用 Unity 构建设置。跨机器联机时配置 [AutoStartClient.connectAddress](../Assets/Core/Prefabs/NetworkManager.prefab#L142) 为服务器可达地址，并确认 UDP 7777 的路由和防火墙允许流量。
