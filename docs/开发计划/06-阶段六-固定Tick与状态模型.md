# 阶段六：固定 Tick 与状态模型
> 前置：阶段五完成；交付：可由单机、回放和服务器共同驱动的玩法模拟
## 1. 输入帧与状态
`InputFrame` 包含玩家标识、输入序号、目标 Tick、移动方向、朝向意图、跳跃、冲刺、拾取、投掷、使用药水和瞄准方向。真人采集器、机器人、回放读取器和网络输入接收器统一生成输入帧，玩法模拟只消费输入帧。网络输入代表玩家意图，不携带可直接覆盖权威 `PlayerState` 的位置、速度或命中结果；输入序号与目标 Tick 用于去重、排序和确定处理范围。
统一移动方向的坐标语义：首版由输入采集器将相机相对输入转换为世界水平面方向，并单独记录朝向意图。运动模拟不得读取 `Camera.main` 或客户端相机 Transform；服务器限制方向长度、转向和动作条件，而不是直接接受客户端旋转结果。跳跃等单次动作记录为消费一次的事件，不能因补帧或重复包重复触发。
`PlayerState` 保存位置、旋转、速度、地面、动作、生命、生存、冲刺、药水、持有道具、最近作用和分数；`ItemState` 保存类型、实例、位置、旋转、速度、生命周期、持有者、作用者和倒计时；`RoundState` 保存阶段、Tick、分数、胜者、复活队列和事件。模拟器拥有状态写入权，Unity 表现层只读取状态并呈现。
### 运动状态的保存与恢复
沿用现有 `CharacterMotor` 的受约束运动，不另起完整刚体角色方案。把影响后续运动的内部数据显式纳入可保存状态，包括水平/垂直速度、接地和动作状态、冲刺/跳跃计时、冷却、输入缓冲及击退参数；阶段八必须能恢复这些数据，不能只恢复 Transform。位置恢复后重新查询接触，不能把 Unity 碰撞对象引用当作可序列化状态。
普通状态与输入结构不持有相机、Animator、GameObject 等表现引用；Unity `CharacterController`、碰撞查询和物理适配仍可依赖 Unity。可序列化不等于脱离 Unity 也能运行全部物理，更不等于跨机器确定性。
## 2. 固定 Tick
以 30Hz 起步。每 Tick 依次读取并选择输入、更新回合、更新角色、处理碰撞与推挤、更新道具、更新药水、更新酸雨、处理死亡与计分、生成事件并输出 `GameState`。模拟时钟统一处理暂停、结算、重开和时间语义。明确缺失输入、重复输入、过期输入和超出可接受未来 Tick 的处理策略。
单机阶段由本地模拟入口推进；网络阶段同一模拟入口由服务器独占调用并写入权威状态。运动使用固定步长，不再按渲染帧的 `Time.deltaTime` 推进。服务器的角色碰撞根节点由模拟入口更新；客户端展示节点、动画、粒子、音效、镜头和 UI 读取状态与事件。不得让 NetworkTransform、客户端脚本或表现回调绕过模拟器修改网络权威位置。
## 3. 随机数与回放
游戏状态保存随机种子和推进状态，道具刷新、药水映射、酸雨触发和安全区选择使用可记录随机数。回放保存初始配置、随机状态、每 Tick 输入、关键事件和周期摘要。
回放不承诺跨机器 PhysX 位级一致，比较回合结束 Tick、淘汰顺序、分数、胜者、关键道具状态和位置误差范围。三局回放的关键结果一致后进入 Mirror 联机阶段。
## 4. 完成标准与测试
□ 30Hz 固定 Tick 推进；
□ 渲染帧率变化不改变关键结果；
□ 玩家、道具、回合和事件使用普通状态；
□ 表现层单向读取；
□ 真人、机器人和回放共享输入帧；
□ 随机状态可记录和恢复；
□ 三局回放结果一致；
□ 状态可脱离 Unity 对象序列化；
□ 运动状态可保存、恢复，模拟不依赖客户端相机或 Animator。
测试 30、60、120 渲染帧率、暂停恢复、回合重开、真人替换机器人、真人替换回放、随机结果复现和同 Tick 多事件顺序。验证相同有效输入在相同模拟条件下的状态转换，并检查表现层没有反向写入状态。逐步迁移玩家、回合、道具和事件，避免一次性抽取造成回归。本阶段不实现 Mirror 权威传输或客户端预测，它们分别属于阶段七和阶段八。
