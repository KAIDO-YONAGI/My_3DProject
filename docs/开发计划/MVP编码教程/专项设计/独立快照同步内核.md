# 独立快照同步内核

## 什么时候使用

只有在平台数量或更新频率使逐对象 `NetworkTransformReliable` 的带宽、CPU 或序列化成本成为实测瓶颈，并且需要跨对象统一 Tick、基线压缩或缺失恢复时，才采用批量快照。它是可独立阅读和实现的进阶专题，不是 MVP 主线前置步骤。

前置知识是 Mirror 的连接与 Spawn 生命周期、消息注册、客户端/服务器执行侧、量化误差和环形缓冲区。专题不依赖其他教程章节中的自定义类型，也不要求替换现有场景、NetworkManager、NetworkPlayer 或玩家移动。

## 如何接入当前工程

将其作为平台位姿的独立替代实验，不混用两种位姿源：

1. 先保留当前 NetworkManager 与玩家 `NetworkTransformReliable.ClientToServer`。
2. 在独立测试分支或可控场景规模中，仅选择平台位姿作为实验对象；平台业务拓扑仍由现有 SyncList、SyncVar 管理。
3. 使用现有 Mirror 消息注册生命周期承载自定义服务器到客户端数据，不增加第二个 NetworkManager。
4. 普通客户端平台仍保持 Kinematic，只从一个明确的数据源更新位姿。
5. 对照逐对象变换同步的消息量、服务器耗时、客户端缓冲内存、显示误差和恢复时间，再决定是否替换。

Mirror 的网络对象标识用于关联平台实体；快照协议只承担批量运动样本，不重新实现对象 Spawn、格子拓扑或比赛状态。

## 协议职责

最小的完整快照需要明确：

| 字段 | 目的 |
| --- | --- |
| 协议版本 | 拒绝无法解读的数据布局 |
| 回合或场景代号 | 丢弃上一局残留数据 |
| Tick 或采样序号 | 排序、插值和识别重复状态 |
| 对象标识 | 将样本关联到已 Spawn 的平台 |
| 基线编号 | 确认差量解码所依赖的完整状态 |
| 位置与旋转 | 表达平台当前位姿 |
| 可选线速度与角速度 | 仅在客户端预测或短时外推确有需要时携带 |

业务字段通过已有 Mirror 状态同步维护。批量快照不能替代 `Cells`、`Anchored`、`Layer`、`RoundId` 或网络对象生命周期。

## 基线与恢复流程

1. 服务器周期性发送完整平台位姿基线，为该基线分配单调编号。
2. 后续样本携带明确基线编号，并只引用该基线中存在的平台。
3. 客户端按回合、对象标识和基线编号验证样本，再将可解码状态放入有界环形缓存。
4. 缺少基线的差量不参与显示；客户端合并重复恢复请求，等待完整基线。
5. 完整基线到达后清除旧代缓存，再接受基于该基线的样本。
6. 平台生成、销毁或新回合开始时更新对象集合或代号，丢弃不匹配的旧状态。

为不同消息选择通道时，按可靠性、时效性和恢复策略设计：可丢弃的高频样本与必须到达的基线/恢复控制信息职责不同。不能仅把全部消息设为 Reliable 就视为完成恢复设计。

## 验证重点

以相同场景、平台数量、采样频率和网络条件，对照 Mirror 逐对象位姿同步与批量快照。记录每客户端业务载荷、服务器序列化耗时、客户端缓存占用、位置/旋转误差、丢包后的恢复时间和晚加入首个完整状态时间。性能结论必须对应这些实测条件；方案说明和简历表达见[物理同步与简历表达](../../物理同步自研方向与简历表达.md)。
