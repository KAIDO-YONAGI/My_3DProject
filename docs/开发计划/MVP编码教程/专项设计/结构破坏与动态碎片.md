# 结构破坏与动态碎片

## 什么时候使用

平台由可破坏格子构成、断开后需要判断哪些部分仍有固定支撑时，使用格子占用集合加四邻接图搜索。该结构是玩法数据，不需要先构建自定义网络快照协议。

## 玩法结构

开局平台位于围栏内，由中心 `3×3` 格组成。下层平台为 `9×9`，中心 `3×3` 留空；玩家跳出开局平台后可落到第二层，未跳出则落到第三层。场地约五层，越低层道具越多。第三层开始按固定频率生成道具，并限制每层库存上限。

玩家按 E 对范围内格子发起攻击。服务器检查目标有效性与攻击范围，移除命中的格子，再按四邻接关系对剩余格子执行 BFS 分组。与固定支撑连接的部分保持锚定；失去支撑的连通部分成为动态平台块。

## 数据和同步职责

1. `PlatformChunk.Cells` 保存该块拥有的格子编号。
2. `Anchored`、`IsOpening`、`Layer`、`RoundId` 描述平台当前状态。
3. `ArenaPlayerActions` 接收本机 E 输入并通过玩家 Command 请求挖掘。
4. 服务器校验玩家、格子、平台和回合，再修改拓扑并运行 BFS。
5. 对每个断开的连通部分建立或更新网络平台对象，复制对应格子与初始状态后由服务器 Spawn。
6. 服务器物理驱动动态块，普通客户端按平台 NetworkTransform 接收位姿。

四邻接搜索只决定格子连通关系。教程用外边缘格子作为锚点：旧平台原本固定，且新组仍含至少一个外边缘格子时，新组保持固定。主线道具只命中仍固定的平台，动态碎片供角色站立、跳离和碰撞；`PlatformChunk.ServerBreak` 自身保留对传入格子执行分组的能力。

## 与角色的关系

平台成为动态块后，`PlatformPassenger` 与现有 `CharacterMotor` 处理支撑位移和离台速度继承。玩家仍按当前拥有者移动链同步；平台的破坏、刚体运动和是否锚定由服务器裁决。

## 收敛规则

同一回合内，挖掘请求由服务器串行处理：先验证并移除格子，再完成分组和平台对象变更，最后更新回合状态。重复或过期的请求在服务器侧拒绝。游戏以掉入 Void 淘汰玩家、只剩最后一名存活者结束回合。

API 及 Prefab 接入点见[集合、公共对象与消息](集合公共对象与消息.md)和 [Mirror 网络 API 总览](../Mirror网络API总览.md)。
