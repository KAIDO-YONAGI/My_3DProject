# 代码生成与序列化

## 什么时候使用

使用 Command、RPC、SyncVar、SyncList 或 Mirror 网络对象时，需要知道 Unity 编译阶段的 Mirror Weaver 怎样把声明变成可运行的网络调用。默认沿用 Mirror 自动生成与序列化；只有数据布局或性能有明确要求时，才考虑自定义序列化。

## Mirror 自动生成的职责

Mirror 的 Weaver 在程序集处理中识别网络组件和特性，为远程调用、同步字段及支持的网络数据生成相应代码。运行时 Command、RPC 和 SyncVar 因此能使用组件声明的字段与方法；调用方不需要自行拼接 RPC 消息。

教程中的 `ArenaPlayerActions` Command、`PlatformChunk` SyncVar 与 SyncList、平台 `NetworkTransformReliable` 都沿用 Mirror 已有机制。它们各自承担输入请求、当前业务状态、集合拓扑与连续位姿，不需要再实现一套字节编码入口。

## 自定义数据类型

给 Command、RPC 或网络消息传递自定义结构时，先确认字段类型受当前 Mirror 版本支持，并检查 Weaver 编译结果。结构保持确定、有限、可验证；避免把 Unity 场景对象引用或整块运行时对象图直接当作网络参数。

需要自定义读写时，发送端与接收端必须使用完全相同的字段顺序、宽度和条件分支。为协议版本或不同消息类型建立明确标识，并用固定样本验证序列化与反序列化一致。该工作属于单独协议的工程责任，不属于 MVP 的 Mirror API 入门步骤。

## 排错路径

1. 读取 Unity Console 的 Weaver 或编译错误，定位不支持的特性、类型或方法签名。
2. 确认组件继承 `NetworkBehaviour`，网络 Prefab 上存在 `NetworkIdentity`。
3. 确认网络对象由服务器 Spawn，且预制体已注册。
4. 检查双方程序集使用相同类型定义与 Mirror 版本。
5. 自定义协议时加入序列化往返测试和版本边界测试，再接入网络运行。

同步 API 的业务选择见 [Mirror 网络 API 总览](../Mirror网络API总览.md)；批量位姿的协议设计只在有测量依据时参考[独立快照同步内核](独立快照同步内核.md)。
