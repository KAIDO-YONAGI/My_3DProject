# 12 运行验收

本章使用第 10 章的一个窗口化 Server 与两个独立 Client。每项实验按准备、动作、预期和失败定位执行。先完成画面与输入实验，再用调试器观察服务器内部规则，最后采集性能数据。

## 1. 准备运行与记录

1. 执行第 11 章 PowerShell 块 1，保存临时目录中的 `build.log`、`run.log` 和 PASS 行。
2. 在 Unity 导入 01 至 09 章全部代码，确认 Console 的 C# 与 Weaver 错误为零。
3. 使用第 10 章的 `MvpArena` 开发构建。需要变量断点时勾选 Script Debugging；三个进程使用同一组构建文件。
4. 启动 Server S、Client A、Client B，使用 `localhost` 和 UDP `7777`。两个客户端连接后，各自用短距离移动确认本地拥有者对应的 `Player <Id>`。
5. 记录构建路径、场景、Unity 与包版本、三个进程 ID、地址、端口和日志路径。开始录像，使 A、B 的界面与平台同时可见。
6. 实验重新开始时关闭旧窗口，再启动新进程。运行时调试改变的刚体值也随这次重启恢复。

### 现有界面能读取什么

| 位置 | 显示内容 | 读数的含义 |
| --- | --- | --- |
| A、B 顶行 | `Round / Tick` | 客户端接收器的回合与播放时钟，可含小数 Tick |
| A、B 接收行 | `Receive ... B / Invalid ...` | 收到的基线与运动业务字节累计值、数据异常次数 |
| A、B 对象行 | `Bodies / Fragments` | 当前播放状态中的全部业务对象数与碎片对象数 |
| A、B 玩家行 | `Player <Id>: HP / Score` | 该播放状态中的玩家生命与累计分数 |
| S 发送行 | `Send ... B / Step ... ms` | 服务器构造的基线与运动业务字节累计值、最近一次 FixedUpdate 耗时 |

纯 Server 的显示器没有本地接收状态，顶行 `Round/Tick` 来自客户端侧默认值。服务器时间读取 `MvpWorld.Round` 和 `Tick`。客户端的玩家行列出所有玩家，通过编号对应 A、B 的拥有者。独立客户端角色都为青色，服务器角色颜色可以区分出生次序。

事件 `Event/Source`、块归属、支撑身份和恢复队列从下文指定的断点变量读取。记录时填写来源，例如“客户端 A UI”或“服务器 MovePlayer 断点”，这样每个数字都有明确出处。

### 打开调试器与读取变量

以下操作使用安装了“使用 Unity 的游戏开发”工作负载的 Visual Studio：

1. 在 Unity 的 `Edit > Preferences > External Tools` 中选择 Visual Studio 为 External Script Editor。双击教程脚本，打开当前 Unity 工程的解决方案。
2. 在 Visual Studio 选择 `调试 > 附加 Unity 调试器`，选择当前项目的 Editor。按下 Unity 的 Play，再点击 Server，A、B 使用独立构建连接这个编辑器服务器。
3. 单击代码行左侧空白处设置断点。选有可执行语句的行；断点命中时，黄色箭头所指的语句尚未执行。
4. 打开 `调试 > 窗口 > 局部变量` 和 `监视`。局部变量窗口展开当前方法中的字典、数组和对象；监视窗口输入下文指定的字段或表达式。按 F10 执行当前语句，再读执行后的值。
5. 下文的运行时赋值或方法调用放在 `调试 > 窗口 > 即时` 中逐条执行。确认当前调用栈帧是所写的方法，使 `p`、`rb`、`id`、`e` 等局部变量可用。注入前记录原值，实验后重启进程。
6. 需要读取独立客户端时，另开 Visual Studio 窗口，附加列表中对应的调试构建 Player。用第 10 章记录的进程 ID 核对目标；附加后在 `MvpView` 中设断点。

**检查点：** 断点为实心圆，命中后能看到当前方法的局部变量。断点为空心时，先检查附加目标，再核对构建已勾选 Development Build、Script Debugging，最后确认打开的源码对应运行构建。按 F5 继续运行；采集性能前取消所有断点并分离调试器。

## 2. 实验一：连接、拥有者与基础移动

**准备：** 新启动一组 S、A、B，平台保持完整，两名玩家 HP 为 100。

**操作：**

1. A 获得焦点，短按 D，看到移动后立即松开，记下移动玩家的编号。B 的同编号玩家应随之移动。
2. 切换到 B，短按 A，确认另一个编号响应。每次只让一个窗口获得键盘输入。
3. 在 A 的平台内侧短按 W、S，观察角色朝向跟随移动方向。
4. 静止后点按一次空格并松开，观察跳起与落回平台。连续重复三次，中间等角色落地。
5. 按住移动键后松开，观察角色停止主动行走。保持两个客户端运行，记录两端 HP 与 Round。

**预期：** A、B 控制各自的拥有者；对方窗口看见对应运动。跳跃有上升和下降，落地后可再次跳跃。两端看到同一回合和玩家生命，画面允许因播放缓冲存在短暂时间差。

**失败定位顺序：** 窗口焦点 → Input Handling → `Keyboard.current` → `NetworkClient.localPlayer` → 服务器 `ReceiveInput` → `MovePlayer`。客户端发出输入而角色仍静止时，在 `ReceiveInput` 中检查玩家编号、`input.Round`、`input.Sequence` 和 `p.Health`，确认 `InputGate.Accept` 是否接收。

## 3. 实验二：投掷、爆炸与结构断裂

**准备：** 新回合中，两名玩家站在平台两端。投掷方向由最后一次移动方向决定。

**操作：**

1. A 位于左侧时短按 D 面向中央；B 位于右侧时短按 A 面向中央。
2. A 点按 E，观察红色炸弹的抛物线、爆炸闪光与平台变化。第一颗炸弹由服务器引信安排在投掷后的 45 Tick 爆炸，约为 1.5 秒；碎片碰撞或连锁可使它提前触发。
3. 换 B 向中央投掷。等爆炸结束后截取 A、B 画面，记录 Round、Bodies、Fragments、两名玩家 HP。
4. 在同一回合继续投掷三至五次，每次间隔超过半秒，观察灰色固定块分离成黄色碎片。记录每次投掷与爆炸的实际画面；投掷受冷却、回合结束状态和对象预算限制。

**预期：** 炸弹在服务器结算并销毁，结构按连接被切断，离开固定支撑的块组成动态碎片。两个客户端播放相同的结构变化；Fragments 统计碎片根对象，一个包含多个块的碎片计为一个。

### 检查块归属与旋转碎片再次断裂

调试场景需要看清世界坐标。可将 S 换成编辑器 Play 中点击 Server，A、B 继续使用独立构建。保持同一教程场景和参数，在服务器 Scene 窗口开启 Gizmos，运行时的黄色连接线表示仍连通的边。

1. 将调试器附加到编辑器，在 `MvpWorld.Gameplay.cs` 的 `Fracture` 中，`positions`、`oldParents`、`velocity`、`angular`、`rotation` 全部取值之后、删除旧根之前设断点。
2. 投掷使结构断裂。在 Locals 或 Watch 中读取 `cuts`、`groups` 和 `blocks`。`blocks` 有 24 个节点，每个 `Node` 对应一条记录；`Parent == 0` 属于固定结构，其他 Parent 应能在 `bodies` 中找到 `Kind == Fragment` 的对象。
3. 对再次断裂的旋转碎片，记录一个受影响节点 `n` 的 `positions[n]`、旧根旋转和旧接触点速度。单步到新组完成、`NetworkServer.Spawn` 之前，读取新根 `body` 与 `blocks[n].Local`。
4. 在 Watch 中比较 `body.transform.TransformPoint(MvpWorld.U(blocks[n].Local))` 和之前的 `positions[n]`。新块世界位置应连续，旋转继承旧根。新根线速度为组内旧接触点速度的平均值，角速度取 `angular[group[0]]`。

**失败定位顺序：** 炸弹生成与 `fuses` → `Explode` 的中心和选边距离 → `Structure.Cut` → `Fracture` 的旧世界姿态取值 → 新 Parent 与局部坐标 → 客户端 `DrawWorld` 的拓扑版本。

断点会暂停整个服务器，客户端继续运行可能超时；读取后立即继续。断点运行只用于规则证据，性能数据在取消断点后采集。

## 4. 实验三：伤害、淘汰与回合重开

**准备：** 完整平台上有两名存活玩家，记录两人的初始 Score。

**操作：**

1. A 向 B 附近投掷，确认爆炸在 B 附近发生。查看两端 B 的 HP 是否同时在播放到对应状态后减少。
2. 需要确定性地验证淘汰时，B 朝平台外侧行走并坠落。A 留在平台安全位置，观察 B 的 HP 变为 0。
3. 记录 A 的 Score 增加、两端 Round 增长和新平台出现的画面。单一存活者得到一分，服务器在结束判定后的 90 Tick 重开，约为 3 秒。
4. 新回合检查两人 HP 回到 100，分数保留，固定平台恢复，临时炸弹与旧碎片消失。重复三局并记录编号、获胜者与分数。
5. 两名玩家都保持存活时，观察回合达到 900 Tick 的时间限制，约 30 秒。多人仍存活的超时结果按代码的单一存活者条件计分。

**预期：** 伤害与淘汰由服务器统一处理。客户端生命显示在对应播放 Tick 生效；回合切换后地形和玩家状态一起恢复。

**碎片撞击的额外观测：** 在服务器 `CharacterImpact` 的 `speed` 计算后设断点。记录 `other.Kind`、`p.Support`、`relative`、`hit.normal` 和 `speed`。相向法线速度至少为 6 且满足撞击间隔时触发伤害；站在自己的支撑碎片上被前面的条件过滤。随后在 `Damage` 读取 `amount`、`impulse` 与 `p.Health`。自然运行中没有满足条件的撞击时，记录实际接触值，避免把普通表面滑动当作伤害触发。

**失败定位顺序：** `Damage` 的生命与结束状态 → `FinishTick` 的落场条件与存活人数 → `endTick` → `ResetRound` → 客户端新基线和 `visualRound`。

## 5. 实验四：连锁与事件去重

**准备：** 在服务器 `Explode` 开头与发送 `MvpExplosion` 的语句设断点，客户端在 `ReceiveExplosion` 设断点。自然连锁通过两个玩家向中央近距离先后投掷制造。

**操作：**

1. A、B 向中央投掷两颗炸弹，观察爆炸中心间距是否小于 3.5 米。记录每个有效结算的炸弹 `id`、服务器 `Round/Tick`。
2. 读取发送前的 `eventId` 与 `source`。引信触发的来源通常是投掷玩家；附近炸弹被连锁触发时，来源是引爆它的炸弹编号。
3. 为确定性验证重复入队，在服务器第一次有效 `Explode` 的入口、执行 `fuses.Remove(id)` 之前，通过调试器即时求值执行 `explosions.Enqueue(id)`。继续运行，观察同编号再次入队时的条件返回。
4. 在客户端首次收到事件时，记录局部变量 `e` 的 Round、Event、Tick、Source。单步执行到 `events.Add(e)` 之后，使事件进入队列；取消这个接收断点，再通过即时窗口执行 `this.ReceiveExplosion(e)`，传入同一个局部变量。取消断点让这次嵌套调用能直接返回。
5. 检查 `seen`、`events` 与爆炸闪光：相同 `(Round, Event)` 的第二次调用在去重判断返回，队列只增加一份。

**预期：** 同炸弹只经过一次有效伤害、结构和事件结算；客户端相同事件只播放一次。调试注入模拟重复输入条件，录屏与断点值分别说明视觉结果和内部规则。

**失败定位顺序：** `fuses.Remove(id)` 是否先消费 → `causes` 来源 → `eventId` 增长位置 → 客户端 `(Round, Event)` 去重 → `events` 的播放 Tick。

## 6. 实验五：动态碎片支撑与跳离

**准备：** 服务器使用可附加调试器的运行环境。平台碎片自然下落较快，使用运行时刚体参数建立能反复观察的支撑条件。

1. 在 `Fracture` 中完成新刚体的 `velocity`、`angularVelocity` 赋值之后、`NetworkServer.Spawn` 之前设断点。
2. 制造断裂，选择一个包含多个块且仍靠近固定平台的组。记录 `group` 和 `body.Id`。
3. 在即时求值中依次设置 `rb.useGravity = false`、`rb.velocity = new UnityEngine.Vector3(0.2f, 0, 0)`、`rb.angularVelocity = new UnityEngine.Vector3(0, 0.3f, 0)`。这些值作用于当前运行实例，使碎片缓慢平移并绕竖直轴旋转。
4. 取消该断点并继续，让 A 从邻接固定块走上该碎片。录像记录站立、沿表面行走与跳离。

**操作与观测：**

1. 在 `MovePlayer` 的支撑分支中，`carry` 与 `pointVelocity` 赋值后设断点。确认 `p.Support` 等于目标碎片 Id，`p.SupportGeneration` 与根的 Generation 一致。
2. 记录 `p.LocalPoint`、`p.PreviousPoint`、新的 `support.transform.TransformPoint(p.LocalPoint)`。`carry` 等于新世界接触点减旧世界接触点，旋转时离根中心更远的接触点也随之移动。
3. 继续运行并在 A 点按空格。在跳跃分支读 `pointVelocity`、`p.Vertical`、`p.External` 和 `p.Support`。刚设置跳跃时 Vertical 为 `8 + pointVelocity.y`，随后本 Tick 扣除 `20 * Rules.Step`；水平方向的接触点速度加到 External，Support 清零。
4. 重新站上碎片，再投掷使它再次断裂。观察原支撑根销毁后，下一次移动重新查询当前地面：有新碎片接触时记录新身份，失去接触时角色进入下落。
5. 实验结束关闭本组进程，使用原构建启动下一组。

**预期：** 站立随局部点平移与旋转，主动行走更新接触位置，跳离继承刚体接触点速度。`p.Velocity` 表示角色主动速度、External 与竖直分量的合成；站立携带位移另通过 `carry` 进入控制器 Move，比较速度时分清这两项。

**失败定位顺序：** Ground 命中碰撞器 → 碎片的 Id/Generation → LocalPoint 与 PreviousPoint → carry → 跳跃条件 → `CharacterController.Move` 后的再次探测。单看客户端插值位置只能确认表现，服务器变量说明支撑算法。

## 7. 实验六：中途加入、重连与缺失基线

### 中途加入

**准备：** S、A、B 保持运行。在新回合初期制造断裂并改变玩家 HP，趁当前回合仍存在破坏状态进行加入。

1. 再启动一个相同构建窗口 C，填 `localhost` 并点击 Client。它成为第三名玩家，服务器的新增玩家与回合判定也包含它。
2. 等 C 出现平台和玩家行，记录 C、A 的 Round、Fragments 与同编号玩家 HP。比较静止块归属和活动碎片，运动物体用各自播放 Tick 解释短暂位置差异。
3. A 继续投掷，观察 C 接入后持续收到后续结构变化。

**预期：** C 通过当前完整基线恢复现有结构和生命，随后播放新运动与爆炸。玩家生成增加拓扑版本，下个 Tick 的完整基线提供新的世界状态。

### 断线再连接

1. 记录 B 当前的玩家 Id，关闭 B 窗口。
2. A 观察该玩家退出。服务器在剩余存活人数满足条件时可以开始回合结束，记录当时 Round。
3. 重新启动 B，点击 Client。记录新玩家 Id 与当前回合，验证 B 输入作用于自己的新玩家。

**预期：** 新连接取得当前状态和新的业务玩家编号。恢复比较以重连时的服务器回合为基准。

### 确定性检查缺失基线恢复

1. 将调试器附加客户端 A，在 `MvpView.ReceiveMotion` 的 `replica.ReceiveMotion(bytes)` 调用前设断点。
2. 先记录 `replica.Round` 与 `Wire.Header(bytes)`。通过即时求值执行 `replica = new Mvp.Replica()`，使当前运动包暂时没有对应基线。
3. 单步执行原来的接收调用，读取 `replica.NeedsBaseline == true`，`replica.PendingCount` 至少为 1。
4. 在 `RequestRecovery` 中实际 `NetworkClient.Send` 语句设断点并继续，记录这次真正发送的 `MvpRecover.Round` 和 `nextRecovery`。只有通过 Ready 与半秒节流判断才到达这个停点。
5. 服务器在 `Recover` 读取 `body.Id`、请求回合、`Tick`、`lastRecovery` 和 `dirty`。恢复请求通过服务器身份与 15 Tick 节流条件后，使下一次采样发送完整基线。
6. 客户端在 `ReceiveBaseline` 观察 `replica.ReceiveBaseline` 返回后状态。有效基线重放等待队列；当前基线对应的包消化后，`NeedsBaseline` 回到 false，PendingCount 回落。

周期性完整基线也能完成这次恢复，因此记录实际接收的基线 Tick 与请求是否真正通过服务器条件。恢复次数用调试器在实际 Send 语句上的命中次数记录，并限定同一次连接；进入 RequestRecovery 方法的次数包含被节流的调用。

旧回合包、身份代次、先运动后基线与有界队列的可重复证据来自第 11 章 `ReplicaTests`。真实传输实验可以在外部网络工具配置延迟与丢包后重复中途加入和重连，记录工具、作用方向、延迟值、丢包率及两端结果。

**失败定位顺序：** Ready 与拥有者 → 请求节流 → 服务器 Recover 条件 → PublishBaseline → 基线身份 → pending 重放 → 网络对象身份 → DrawWorld。

## 8. 采集性能和业务字节

取消所有断点，固定运行配置和操作序列。例如每局开始两人静止 5 秒，随后 A、B 各向中央投掷 3 次，记录每次投掷时刻。启动后预热 30 秒，每组采样 60 秒，重复三组。采样可以跨回合，记录每次 Round 切换；断线或停止服务器导致计数重置时开始新样本。

| 数据 | 具体读取动作 | 解释范围 |
| --- | --- | --- |
| 服务器 Step | 录制 S 的 `Step`，按固定时间点抄录 | 最近一次 FixedUpdate，包含角色、物理、回合和编码发送路径 |
| 服务器业务字节 | 采样起止读取 S 的 `Send`，计算 `(结束值 - 起始值) / 秒数` | 每次基线和运动批次构造的 byte[] 累计值 |
| 客户端业务字节 | 分别读取 A、B 的 `Receive` 起止值 | 该客户端计入接收统计的基线与运动载荷 |
| 对象与碎片 | 从 A 或 B 的 `Bodies/Fragments` 按时刻记录 | 播放状态的业务根数量，碎片块数从 blocks 另行观察 |
| 坏包次数 | 记录各客户端 `Invalid` 起止值 | 数据读取异常计数；丢包率由网络工具配置或抓包统计 |
| 脚本与物理耗时 | `Window > Analysis > Profiler`，选择服务器进程，开启 CPU Usage、Physics，Record 采样并保存 | Timeline 找 `MvpWorld.FixedUpdate` 与物理采样；Deep Profile 开关随结果一起记录 |
| 结构函数耗时 | Profiler 开启 Deep Profile，查看断裂帧中 `Fracture` 与 `Structure.Cut` 的调用 | 带分析器开销的结构路径测量，单独保存这组数据 |
| 实际网络带宽 | 抓包工具筛选 UDP `7777`，按源与目标连接统计指定时间窗口 | 包含 Mirror、KCP 与抓包工具统计口径中的协议开销 |

`BytesSent` 每次广播构造载荷累加一次，多个连接收到同一载荷时仍只累加一次。爆炸消息、输入消息、Mirror 对象消息和 KCP 开销由网络统计覆盖。用业务字节比较编码成本，用抓包数据比较实际传输。

量化精度记录第 11 章的协议断言。比较服务器与客户端位置时，先对齐 Round、Version、对象 Id/Generation 和状态 Tick；同一墙钟时刻的服务器位置与客户端插值位置代表不同模拟时间。
