# 物理同步方向与简历表达

## 当前工程事实

当前工程使用 Unity 与 Mirror，场景按 `InitialScene → PersistentScene → MultiplayerSampleScene` 进入玩法；网络连接沿用现有 `NetworkManager.prefab`、KCP UDP 7777 和 `AutoStartClient` 配置。

`NetworkPlayer.prefab` 的角色移动由拥有者本机 `CharacterMotor` 驱动，玩家位姿通过 `NetworkTransformReliable.ClientToServer` 上行；`CharacterMotionSync` 同步动画参数，`NetworkAudioPlayer` 处理网络音频。`ThirdPersonCamera` 可跟随本机角色，观战目标需要本地代理，避免相机旋转写入远端玩家 Transform。

现有联机能力与新增 MVP 玩法分别记录，简历成果按实际运行证据确定。MVP 直接扩展本工程的 `NetworkPlayer` 和 `MultiplayerSampleScene`。

## MVP 教程的实现边界

MVP 直接扩展现有工程：在现有 `NetworkPlayer` 上增加 `ArenaPlayerActions`、`PlatformPassenger` 和 `ArenaPlayerPresentation`，使用 `Core.Scripts.Gameplay.Mvp` 命名空间；沿用原有角色 Prefab、场景和 NetworkManager。

玩法侧的服务器权威范围是平台物理与破坏、道具状态和胜负结算。玩家移动仍由拥有者 `CharacterMotor` 驱动，方向仍为 ClientToServer；动态平台使用 `NetworkTransformReliable.ServerToClient`，普通客户端刚体保持 Kinematic。角色支撑平台的位移和跳离速度接入现有 `Move` 流程。

主线平台使用 `SyncList<int> Cells` 表示格子集合，使用 `Anchored`、`IsOpening`、`Layer`、`RoundId` 描述当前状态。服务器以四邻接 BFS 分组断裂格子，`ArenaMatch` 管理回合、胜负和道具生成，`ArenaPickup` 检查接近并发放使用次数，库存由玩家的 `ArenaPlayerActions.Charges` 保存。客户端显示同步结果。网络交接采用 Mirror 现有 Command、SyncVar、SyncList、NetworkTransform、Spawn 和 RPC。

双客户端验收口径包括开局双人近距触发炸弹、E 键服务器验证挖掘、格子断裂与支撑、约五层场地、道具库存、Void 观战、最后存活者结束回合，以及晚加入时的平台当前状态和位姿。

## 物理同步的研究方向

先用 Mirror 的逐对象 NetworkTransform 完成平台同步，再根据可复现的性能数据决定是否需要批量快照。独立快照专题聚焦平台位姿量化、统一 Tick、基线编号、差量解码、缺失基线恢复和有界缓存；它不替换 NetworkManager、NetworkPlayer 或玩家移动，也不承担平台格子与回合业务状态。

比较时保持场景、平台数、采样频率、运行时长和网络条件一致，分别记录客户端业务载荷、服务器序列化耗时、客户端缓存、位置与旋转误差、晚加入首帧时间和丢包恢复时间。只有实测结果支持的性能改善才写成量化结论。

## 简历表达

以下内容区分工程现状与新增 MVP 的实现结果。现状可以按代码直接描述；新增玩法在完成实现并取得双客户端证据后，采用对应句式。

### 当前工程

> **Unity / Mirror 联机角色框架**：维护现有场景与 NetworkManager 流程，基于 Mirror 同步玩家角色选择、动画状态和拥有者驱动的角色位姿；玩家移动采用 ClientToServer 同步。

### 新增 MVP：玩法与平台物理

> **Mirror 平台破坏 MVP**：在现有玩家与场景框架中实现服务器裁决的平台破坏、动态平台、道具和回合胜负；以格子连通分组识别断裂块，并将动态平台位姿同步到普通客户端。

### 新增 MVP：混合权威与角色接入

> **联机角色与动态支撑**：保留拥有者驱动的 CharacterMotor 和 ClientToServer 玩家位姿同步，在现有 Move 流程接入动态平台支撑位移与离台速度继承；服务器负责平台物理、道具及胜负裁决。
