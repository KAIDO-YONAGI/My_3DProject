## 生命周期中的代码放在哪里

### 1. 网络对象的创建链路

项目通过 [AutoStartClient.cs](../../../Assets/Core/Scripts/Networking/Connection/AutoStartClient.cs) 使用 `NetworkManager.networkAddress` 连接服务器。

`NetworkManager` 是 Mirror 的启动、连接与玩家创建管理器。Transport 是 Mirror 的字节传输接口，本项目使用 `KcpTransport`，在 UDP 上提供可靠与非可靠通道。服务器监听 UDP `7777`。

玩家创建链路是：

```text
客户端连接成功
  → Ready，声明准备接收网络世界
  → AddPlayer，请求为连接创建玩家
  → 服务器选择出生点
  → 服务器创建 NetworkPlayer
  → AddPlayerForConnection 建立玩家归属
  → Spawn 向客户端发送对象与初始状态
  → 客户端启动回调建立本地表现
```

本项目 `InitialScene` 加载 `PersistentScene`，常驻场景带入网络与表现管理器，玩法场景由 `SceneChanger` 加载。配置入口见 [Mirror_KCP_Config.md](../../../Y_MultipleAgentWorkflow/Project/Mirror_KCP_Config.md)。

### 2. 各回调承接各自职责

| 位置 | 适合编写的内容 |
| --- | --- |
| `Awake` | 缓存本地组件、创建纯计算对象、整理依赖 |
| `OnStartServer` | 初始化服务器状态、登记服务器业务关系 |
| `OnStartClient` | 按已接收状态建立客户端表现、订阅同步集合 |
| `OnStartLocalPlayer` | 绑定本地玩家界面、配置本地输入与相机 |
| `OnStartAuthority`、`OnStopAuthority` | 处理可转移归属对象的本地控制启停 |
| SyncVar hook | 将变化后的状态应用到本地表现 |
| Command 方法体 | 校验客户端请求、调用服务器业务逻辑 |
| ClientRpc、TargetRpc 方法体 | 处理接收到的客户端通知 |
| `OnStopClient` | 解除客户端订阅、清理视觉实例和引用 |
| `OnStopServer` | 清理服务器登记与业务引用 |
| `OnDestroy` | 释放该实例持有的本地运行时资源 |

`Awake` 面向 Unity 实例初始化。网络身份和初始状态相关逻辑放入相应网络回调，输入处理继续检查当前对象的身份。

### 3. 初始化读取与变化订阅配套

建立状态驱动的 UI 或表现时使用同一规则：

```text
绑定对象
  → 读取当前值，建立完整显示
  → 订阅后续变化

接收变化
  → 更新对应显示

解绑对象
  → 解除订阅
  → 清理引用与表现
```

启动回调和 hook 都可能触发刷新，刷新方法按当前状态实现幂等。项目 `presentations` 缓存是这种做法的具体实例。

官方依据：[NetworkBehaviour](https://mirror-networking.gitbook.io/docs/manual/components/networkbehaviour)、[SyncVars](https://mirror-networking.gitbook.io/docs/manual/guides/synchronization/syncvars)、[SyncLists](https://mirror-networking.gitbook.io/docs/manual/guides/synchronization/synclists)。

## 编写边界与开发步骤

### 1. Mirror 处理传输，开发者处理游戏规则

| Mirror 提供的能力 | 开发者需要决定的内容 |
| --- | --- |
| 连接、消息传输与网络生命周期 | 连接进入哪个房间、何时允许加入游戏 |
| 网络身份与对象归属 | 玩家控制哪些实体、哪些操作开放给非拥有者 |
| Command 默认归属检查 | 参数、距离、冷却、消耗、状态和频率检查 |
| SyncVar 与同步集合 | 谁写状态、哪些数据对哪些客户端可见 |
| RPC 参数发送与接收 | 事件内容、目标连接、重复处理规则 |
| 变换与刚体同步组件 | 用于教学和对照的运动采样与显示配置 |
| 自定义消息与传输接入 | 正式交付的快照格式、基线、预算、时间轴和插值内核 |
| 序列化代码生成 | 数据结构、资源编号和双端协议一致性 |

构建网络功能时，先定游戏规则，再选择框架机制。框架让数据抵达正确位置，游戏代码决定抵达后的含义。

正式交付的六类网络逻辑、恢复流程和独立测试统一见 [独立快照同步内核](专项设计/独立快照同步内核.md)。结构算法、碎片与角色接触的验收见 [结构破坏与动态碎片](专项设计/结构破坏与动态碎片.md#验收与测量)。

### 2. 远程方法按框架要求编写

Command、ClientRpc 和 TargetRpc 使用实例方法，返回类型为 `void`，参数使用 Mirror 支持序列化的类型。

开发中优先使用简单数值、枚举、向量、小型结构体和有效网络对象身份。自定义类型需要对应读写能力，写入与读取的字段顺序保持一致。

远程方法采用普通、非泛型签名。操作结果通过状态同步或单独响应返回，客户端以回调处理异步结果。

`CommandSetCharacter` 的 `int` 参数和 `void` 返回类型正是这种写法。它通过 SyncVar 返回确认状态。

### 3. 同步范围按数据用途设置

面向其他玩家可见的状态使用观察者范围。只有拥有者需要的数据可以在对应网络组件上使用 `Owner` 同步模式，即向拥有者同步。

同步模式属于组件配置。公开数据和私有数据需要不同发送范围时，按职责分到相应组件。

RPC 同样选择合理范围：ClientRpc 面向当前对象的观察者，TargetRpc 面向指定连接。接收端需要存在对应网络对象的副本，才能在该对象上执行远程通知。

Interest Management 是 Mirror 的兴趣管理机制，负责决定每个连接观察哪些网络对象。按房间、场景、距离或队伍划分观察范围时，服务器据此控制对象生成消息、状态和观察者通知的接收范围。

设计数据发送时分三层确定：

1. 兴趣管理确定这个对象对哪些连接可见。
2. 组件同步模式确定状态面向观察者还是拥有者。
3. RPC 选择本次事件面向观察者还是指定连接。

本地关闭模型属于显示处理。需要控制网络数据的接收范围时，在服务器的观察规则与组件同步模式中安排。

客户端查找网络引用时按自己的已生成对象表处理。服务器已存在的实体，在某个客户端上是否存在副本取决于该客户端的观察范围和生成时机。

官方依据：[Interest Management](https://mirror-networking.gitbook.io/docs/manual/interest-management)、[Synchronization](https://mirror-networking.gitbook.io/docs/manual/guides/synchronization)、[Remote Actions](https://mirror-networking.gitbook.io/docs/manual/guides/communications/remote-actions)。

### 4. 每次添加功能按同一顺序完成

1. 写出对象、请求者、决定者、接收者和初始恢复规则。
2. 在网络根上定义最少的同步状态。
3. 在本地控制层定义一个明确的请求入口。
4. 使用 Command 或 NetworkMessage 建立上行。
5. 在服务器入口完整校验，再修改服务器业务状态。
6. 使用 SyncVar、集合或响应消息建立下行。
7. 在客户端接收入口调用普通表现代码。
8. 用当前值初始化，并补齐订阅与资源清理。
9. 核对 Prefab 注册、组件顺序、同步方向和编号含义。
10. 使用匹配构建验证服务器、拥有者、远程观察者和后加入者。

对角色切换，这十步分别落在玩家网络根、`characterId`、`SetLocalCharacter`、`CommandSetCharacter`、编号校验、SyncVar、表现管理器、启动与停止回调、两套角色数组和多客户端验证中。

### 5. 验证按链路逐段观察

验证角色切换时，先启动专用服务器，再连接两个客户端：

| 观察位置 | 检查内容 |
| --- | --- |
| A 的按钮回调 | 点击触发，解析到 A 的当前本地玩家 |
| A 的 `SetLocalCharacter` | 本地身份与编号校验通过 |
| A 的发送入口 | 连接就绪、对象已生成、具备发送权限 |
| S 的 Command 入口 | 方法被定位，请求参数正确 |
| S 的业务处理 | 编号通过校验，服务器字段更新 |
| A、B 的同步字段 | 甲的编号与服务器确认值一致 |
| A、B 的表现管理器 | 同编号映射到正确的本地或远程资源 |
| 后加入客户端 | 直接按甲的当前编号建立表现 |
| 玩家断开后的客户端 | 视觉实例、缓存和订阅完成清理 |

移动验证分别观察拥有者计算、服务器接收、远程插值和动画表现。

项目相机在按住 `Alt` 时释放光标，界面操作可以使用这条本地输入路径。排查按钮操作时，先确认点击进入回调，再沿上行与下行检查，按阶段记录实际结果。

日志可以包含进程角色、`netId`、操作名称、请求参数和确认状态。它们帮助区分本地调用、网络发送、服务器接收和客户端应用。

写联机功能时始终保留这条主线：

```text
本地对象收集意图
  → 网络组件提交请求
  → 服务器决定状态
  → 网络组件传递状态或事件
  → 本地对象完成显示
```

需要采用拥有者计算的连续数据时，像项目移动一样为它单独定义上行和下行，并明确服务器在链路中的职责。
