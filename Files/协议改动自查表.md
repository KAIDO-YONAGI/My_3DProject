# 协议改动自查表

## 核心原则

> 这条消息从"谁发出"到"谁收到并真正生效"，中间每一层我都改到了吗？

改协议不能只改一个 `Protocol.cs`，必须按完整链路检查：

```
协议定义 → 客户端发包 → 服务端收包解析 → 服务端状态更新 → 服务端回包/广播 → 客户端拆包 → 客户端监听注册 → 客户端业务落地 → 联调验证
```

## 网络层注意事项

### 线程安全

| 规则 | 原因 |
|------|------|
| 不在异步网络线程直接调用 Unity API | Unity API 只能在主线程使用 |
| 不在 `lock` 作用域内 `await` | `lock` 要求同线程加解锁，`await` 会切换线程 |
| 不绕过 `sendLock` 直接 `SendAsync` | 同一 socket 并发发送会导致数据交错 |
| 用 `ConcurrentQueue` / `ConcurrentDictionary` 传递跨线程数据 | 普通集合不是线程安全的 |

### 半包/粘包

客户端 `AppendMessages()` 和服务端 `TryReadMessage()` 都保留了未完成片段，只有遇到完整 `\n` 才继续解析。如果以后改分包规则，两端必须同时改。

### 发送完整性

`SendAllAsync` 用 `while` 循环保证所有字节发完，因为 TCP 一次 `SendAsync` 可能只发出部分数据。新增发包逻辑时必须保留此模式。

### 连接生命周期

- `Connect()` 是"发起连接"不是"连接完成"，后续逻辑要等连接结果事件
- `Disconnect()` 先发 Leave 再清理，但对外是 fire-and-forget
- `CloseSocket()` 幂等：Cancel → Shutdown → Close → 置空
- 服务端 `RemoveClient()` 幂等：TryRemove → 关闭连接 → 广播 Leave

### 写新功能时自问

1. 这段逻辑在主线程还是线程池？
2. 这条消息可能被拆成两次 `Receive` 才收完整吗？
3. 这次发送可能和同一 socket 上另一条发送重叠吗？
4. 断线/重连/重复清理时这段逻辑安全吗？
5. 调用方要的是"发起动作"还是"动作完成"？

## 当前未完整打通的功能

- **Attack**：客户端有 `PackAttack()`/`ParseAttackArgs()`，服务端有 `PackAttacked()`，但 `HandleMessage()` 没有 Attack 分支，客户端也没注册监听
- **断线重连**：`ConnectWithRetry` 只运行一次，无真正重连
- **服务端 `PackAttacked`**：`address` 和 `damage` 之间缺少分隔符
- **`PlayerInfoManager`**：已定义但未使用，玩家数据存在 `ClientState` 中
