# My_3DProject 联机闯关开发方案(完整版)

## 一、项目定位与技术选型

| 维度 | 选择 | 理由 |
|---|---|---|
| 玩法类型 | 联机闯关 + 互害互助 | 内容轻、演示效果好 |
| 同步模型 | **状态同步** | 物理混乱 + 跨平台 + 中途加入,帧同步不合适 |
| 网络拓扑 | **专用服务器**(LocalServer 升级) | 最干净、最像商业项目 |
| 玩法驱动 | 混合(数值 + 关卡 + 物理) | 分层落地,先数值后物理 |
| 起点 | 基于 My_3DProject 续做 | 复用已有 TCP 异步层 |

---

## 二、目标架构

```
┌─────────────────┐        ┌─────────────────┐
│  客户端 A        │        │  客户端 B        │
│ ┌─────────────┐ │        │ ┌─────────────┐ │
│ │ RenderLayer │ │        │ │ RenderLayer │ │  ← 角色控制器、特效、UI
│ │ (预测+插值) │ │        │ │ (预测+插值) │ │
│ ├─────────────┤ │        │ ├─────────────┤ │
│ │ NetClient   │ │        │ │ NetClient   │ │
│ └──────┬──────┘ │        │ └──────┬──────┘ │
└────────┼────────┘        └────────┼────────┘
         │ 输入(按键)             │ 输入
         ▼                          ▼
    ┌────────────────────────────────────┐
    │      专用服务器 (LocalServer)        │  ← 权威
    │  ┌──────────────────────────────┐  │
    │  │   GameServerLogic (权威层)   │  │
    │  │  - 血量/状态机(防作弊)       │  │
    │  │  - 道具归属/命中判定          │  │
    │  │  - 物理仲裁(关键事件)        │  │
    │  └──────────────────────────────┘  │
    │  ┌──────────────────────────────┐  │
    │  │   SocketServer (已有)         │  │
    │  └──────────────────────────────┘  │
    └────────────────────────────────────┘
```

**核心原则**:客户端只发"我想做什么"(输入/请求),服务端决定"到底发生了什么"(结果),再广播给所有人。客户端本地物理只是视觉预测,最终以服务端为准。

## 三、玩法驱动分层(混合驱动的落地方式)

物理和数值不要揉一起,分三层,按难度递增上:

| 层 | 内容 | 网络难度 | 何时做 |
|---|---|---|---|
| **L1 数值层** | 血量、道具效果(眩晕/减速)、Buff、复活 | ⭐ 简单 | 先做 |
| **L2 关卡层** | 开关、陷阱、传送门、机关互相影响 | ⭐⭐ 中等 | 第二步 |
| **L3 物理层** | 推搡、投掷砸人、碰撞混乱 | ⭐⭐⭐⭐ 难 | 最后 |

L3 放最后的原因:实时物理同步是网络游戏的"老大难",即使商业项目也用各种妥协。先把 L1/L2 做出来,游戏已经能玩了,物理作为锦上添花。

## 四、开发里程碑(M1-M7)

### M1 · 协议层重构(1-2 周,地基)

**目标**:字符串协议 → 二进制协议 + 协议代码生成器。

**任务**:
1. 从 CardDemo 复制协议工具链到 `Assets/Editor/ProtocolTool/`:
   - `ProtocolTool.cs`(菜单入口)
   - `GenerateCSharp.cs`(XML → C# 代码生成)
   - `ProtocolInfo.xml`(协议定义)
   - `BaseData.cs`(读写原语基类)
   - `BaseMsg.cs`、`MsgHandlerCenter.cs`
2. 用新协议替换旧的字符串协议(`PackMove("x,y,z")` → `MoveInputMsg`)
3. 实现服务端二进制分包(`[msgID(4)][len(4)][body]`)
4. 跑通两端二进制通信

**协议定义草案**:
```xml
<message id="1001" name="PlayerJoinMsg">
    <field type="string" name="playerName"/>
    <field type="int" name="modelId"/>
</message>
<message id="1101" name="MoveInputMsg">
    <field type="float" name="x"/>
    <field type="float" name="z"/>
    <field type="bool" name="jump"/>
</message>
<message id="1102" name="PlayerStateMsg">
    <field type="int" name="playerId"/>
    <field type="float" name="x"/>
    <field type="float" name="y"/>
    <field type="float" name="z"/>
</message>
<message id="2001" name="AttackRequestMsg">
    <field type="int" name="targetId"/>
</message>
<message id="2002" name="DamageMsg">
    <field type="int" name="targetId"/>
    <field type="int" name="sourceId"/>
    <field type="int" name="damage"/>
    <field type="int" name="nowHp"/>
</message>
```

**验收**:两端用二进制消息通信,协议代码全由菜单生成,无手写。

---

### M2 · 服务端权威化(1-2 周,核心转折)

**目标**:服务端从"转发器"升级成"裁判"。

**任务**:
1. **服务端对局状态**:新建 `GameSession` 类,管理 `Dictionary<int, ServerPlayerState>`,含 `Hp/Position/Status`
2. **服务端主循环**:`ServerCore` 加 20Hz update 循环,处理输入、广播状态
3. **权威攻击判定**:
   - 客户端发 `AttackRequestMsg(targetId)`
   - 服务端校验:距离?冷却?目标活着没?
   - 通过 → 算伤害 → 广播 `DamageMsg`
   - 失败 → 丢弃
4. **血量服务端维护**:客户端血量 UI 只能从 `DamageMsg.nowHp` 更新,不允许本地改
5. **房间生命周期**:加入/准备/开始/结束

**架构调整**:
```
ServerCore (网络层,保留)
   ↓
GameSession (新)
   ├─ ServerPlayerState[id] → {hp, pos, status}
   ├─ OnAttackRequest(req) → 校验 → 算伤害 → Broadcast(DamageMsg)
   └─ FixedTick(20Hz) → 广播 PlayerStateMsg
```

**验收**:A 打 B,B 掉血(服务端判的);作弊测试——客户端伪造血量被服务端忽略。

---

### M3 · 玩家本体 + 3C 控制器重构(3-4 周,3C 方向核心)

> 这是按 3C 方向重写的 M3,不是原来"1 周打磨"的版本。

**目标**:抛弃导入的 SimpleActionCharacterController,自研控制器;实现本地预测 + 远程插值。

**三阶段落地**(铁律:先本地 → 再网络 → 最后抽象):

#### 阶段 1:自研最小控制器
```
CharacterMotor (输入→速度→位移,纯逻辑)
├─ 速度/重力/碰撞
PlayerCamera (跟随 + 碰撞避免)
└─ 暂不区分本地远程,先做好手感
```
先写一个最简单的自己实现的控制器(能跑能跳能转视角),跑通后再加网络。不追求 UE 级别的抽象。

#### 阶段 2:加网络,本地预测 + 服务器校正
```
LocalPlayer : CharacterController
├─ 输入 → 立刻预测移动(本地手感)
├─ 20Hz 发送 MoveInputMsg
└─ 收到 PlayerStateMsg → 校正位置(误差大瞬移,小则插值)

RemotePlayer : CharacterController
├─ 收到 PlayerStateMsg → 存入插值缓冲(环形缓冲最近 N 个位置)
└─ Update 里对缓冲做 Lerp 平滑显示
```

#### 阶段 3:重构出统一抽象
```
CharacterController (核心,所有角色共用)
├─ Motor (移动:速度/重力/碰撞)
├─ Animator (动画状态机:Grounded/Jump/Fall/Attack)
└─ InputSource (抽象输入源) ← 关键分叉点
    ├─ LocalInput    (键鼠/手柄 → 立即预测)
    ├─ RemoteInput   (网络包 → 提供目标位置供插值)
    └─ AIInput       (行为树 → 服务端权威)
```

**核心原则**:移动/物理/动画全共用,只在"输入从哪来"上分叉。这是 UE 的 `ROLE_Authority/SimulatedProxy/AutonomousProxy` 思路。

**附加任务**:
- 角色状态机:Idle/Run/Attack/Hit/Dead/Stunned
- 血条 UI:世界空间 Canvas 跟随角色
- 对象池:从 2D-Demo 抄 `PoolMgr`,复用特效/投射物

**验收**:两个客户端看到的对方移动平滑;攻击有起手动画 + 命中特效 + 击退;血条跟随。

### M4 · 道具互害系统(2 周,游戏性核心)

**互害道具设计**(从易到难):

| 道具 | 效果 | 服务端实现 | 难度 |
|---|---|---|---|
| 香蕉皮 | 踩到滑倒(stun 1.5s) | 检测踩踏 → 广播 stun | ⭐ |
| 眩晕手雷 | 范围眩晕 3s | 范围判定 + 广播 | ⭐⭐ |
| 粘液瓶 | 区域减速 50% 持续 5s | 维护地面区域 + debuff | ⭐⭐ |
| 黑洞手雷 | 把附近玩家吸向中心 | 施加向心速度 | ⭐⭐⭐ |
| 弹簧陷阱 | 踩中弹飞 | 施加向上冲量 | ⭐⭐⭐ |
| 投掷箱子 | 物理投掷砸人 | 记录箱子位置 | ⭐⭐⭐⭐ |

**任务**:
1. 道具数据驱动:ScriptableObject 定义道具(图标/效果/冷却)
2. 道具实体:服务端维护 `Dictionary<int, ItemState>`
3. 拾取流程:`PickupRequestMsg` → 验证 → `ItemOwnershipMsg` 广播
4. 使用流程:`UseItemMsg` → 服务端执行 → 广播状态变化
5. 地面残留物:服务端维护一段时间消失的区域

**协议补充**:
```xml
<message id="2103" name="UseItemMsg">
    <field type="int" name="itemId"/>
    <field type="float" name="aimX"/>
    <field type="float" name="aimZ"/>
</message>
<message id="2104" name="ItemEffectMsg">
    <field type="int" name="itemId"/>
    <field type="int" name="effectType"/>
    <field type="list" T="int" name="targetIds"/>
    <field type="float" name="duration"/>
</message>
```

**验收**:至少 3 种互害道具可玩;有冷却 + 有限数量防滥用。

---

### M5 · 物理混乱(2 周,可选/选做)

**任务**:
1. 服务端物理仲裁:推搡/碰撞高频事件,客户端报告 → 服务端校验 → 算击退 → 广播
2. 投掷物物理:服务端记录位置,客户端做物理表现,碰撞结果服务端仲裁
3. 击退/弹飞:服务端施加速度向量,客户端物理层接收并模拟

**降级方案**:如果物理同步太难,降级为数值版——推搡→强制位移+眩晕;投掷→投射物+命中伤害。

**验收**:两个玩家能互相推搡,双方画面基本一致;投掷箱子能砸到人。

---

### M6 · 互助机制(1-2 周)

**互助设计**:

| 机制 | 效果 | 设计点 |
|---|---|---|
| 复活队友 | 倒地队友可被拉起 | 复活需 3s 站桩,期间自身暴露 |
| 治疗光环 | 靠近队友缓慢回血 | 抱团 vs 分散的取舍 |
| 共享护盾 | 替队友挡一次伤害 | 走位配合 |
| 合力机关 | 两人同时踩开关才开门 | 强制合作 |

**任务**:
1. 倒地/复活状态机
2. 治疗光环逻辑(服务端范围检测 + 持续回血)
3. 合力机关(服务端记录开关状态,需多人同时激活)

**验收**:至少 2 种互助机制可玩。

---

### M7 · 关卡与结算(2 周)

**任务**:
1. 关卡设计:1 个完整关卡(起点 → 机关区 → Boss/终点)
2. 关卡状态机:Loading → Ready → Playing → GameOver/Win
3. 关卡机关:门/电梯/陷阱/传送带,服务端权威
4. 结算:全队到终点=胜利;全队死亡=失败
5. 重开:一局结束回大厅 + 准备流程

**验收**:完整一局流程能跑通;关卡里至少 1 个合作机关 + 2 个互害陷阱点。

## 六、技术风险与应对

| 风险 | 应对 |
|---|---|
| 本地预测与服务器校正手感差 | 初期不做预测,先跑"发输入→等结果"朴素版;手感问题明显再加预测 |
| 物理同步 desync | M5 物理混乱做不出就降级为数值版(强制位移 + 眩晕) |
| 服务端跑 Unity 物理 | M5 前不用服务端物理,用纯几何判定(距离/范围);真要物理再考虑 headless Unity |
| 自研控制器手感不到位 | 阶段 1 先做最小可用版本,不追求商业级;参考几款标杆的手感参数 |
| 实习精力不足 | 每个里程碑优先保证"能录视频",功能可砍 |
| 协议生成器适配 | M1 最关键,卡住就单独拆出来集中解决 |
